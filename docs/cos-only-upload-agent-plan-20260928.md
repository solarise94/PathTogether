# 用户上传统一走 COS：Agent 连续执行与旧链路退役方案

日期：2026-09-28。核对基线：PathTogether `a668580`。本文是待实施方案，不是完成或上线报告。

## 1. 目标、裁决和授权边界

所有**新用户上传**统一走“创建 ingestion 任务 → 浏览器上传 COS → 服务端摄取 → 校验/解包/转换 → 统一发布”。文件大小不再选择上传后端；用户不再选择“平台上传/云端直传”。COS 不可用时明确暂停或稍后重试，不自动回退到本地上传。

最终只保留一套新上传控制 API、浏览器传输实现、任务与容量生命周期。复用 `/api/ingestions`、官方 SDK 薄适配、现有 pool、holder、任务存储锁和统一发布原语；不再创建另一套等价 upload/job/reservation 框架。

百度导入、CLI、已有转换任务等内部来源不强制绕传 COS；它们继续共用容量、文件锁与发布原语。本文不把 COS 改成长久资产库：已发布文件仍按现有 slide ID 存储与读取合同管理。

执行 Agent 连续完成第 7 节 U0–U6 的代码与副本验收，不停在方案、局部适配或常规确认上。允许修改相关代码、迁移、测试和文档；保留工作区他人修改，不批量还原/暂存。开始读取适用 AGENTS.md 并检查 HEAD/status。

**不授权生产部署、核账应用、停写、扩池购买、读取生产凭证、发送真实邮件或启用 COS。** 默认 capability 继续 off。真实桶与真实 MRXS 样本等尚无授权/环境的验收列为上线门禁，不伪称完成。代码、测试与迁移方案能够独立推进的部分须全部完成。

相关合同：[容量生命周期](task-capacity-lifecycle-repair-agent-plan-20260927.md)、[R12 连续修复](r12-capacity-lifecycle-fix-agent-plan-20260927.md)、[slide ID 迁移 runbook](slide-storage-migration-audit-runbook-20260925.md)。本文取代 [原 COS 设计](cos-direct-upload-audit-plan.md) 中“手动选路、大小路由、超限退 V2”的产品策略；保留其授权、可信核对、池硬上限、清理和对账合同。

### 2.1 容量矛盾必须显式解决

当前默认用户上传上限 `UPLOAD_MAX_REQUEST_BYTES=10*1024**3`（10 GiB），COS 池 `10_000_000_000` 字节，安全余量 `500_000_000`，可准入仅 `9_500_000_000`。直接切换会缩小原有可上传范围。

本方案不默认降低产品上限、不移除安全余量、不把超大任务永远塞进队列，也不保留 V2 兜底。代码参数化区分：

- **产品文件上限**：单一服务端权威，沿用现有允许上限；旧“单 HTTP 请求体限制”不再代表直传文件上限。保留控制 API 自身的小请求体保护。
- **COS 单任务可准入上限**：池容量减安全余量，必须至少覆盖产品允许的最大原始上传对象；实际可用余额不足则等待。
- **本地处理预算**：解包、转换所需容量与磁盘水位另行保障，不把压缩包体积当作全部本地责任。

切换前发布预检必须证明“池可准入上限 ≥ 产品文件上限”。当前默认配置不满足；Agent 应交付所需容量计算、测试配置和运维配置草案。实际扩大池预算/配置需另行批准；未解决前不得宣布 COS-only 可上线。禁止仅修改展示上限掩盖不兼容。

### 2.2 当前维护核账尚有已复现问题

`a668580` 尚有 R15 复核发现：正常 owner 的无预约上传被核账终止；终态无 pending 残留 repair 后没有持久清理工作。见 [证据](review-evidence/r15/REVIEW.md) 和 [反例](review-evidence/r15/test_r15.py.txt)。执行时若 HEAD 已修复先验证，否则在 U0 修复，不能以统一 COS 为由跳过身份与清理责任。

## 3. 统一任务与身份合同

### 3.1 身份、幂等与状态

- 一个上传原始对象对应一个 ingestion 主任务；原生单文件对应一个资产，ZIP 可产生多个资产，转换可有明确子作业。主任务是用户跟踪、取消、配额模式和失败重试的入口。
- 使用已有任务 ID、服务端随机对象 key 和 slide ID；原文件名只用于展示和格式提示。所有任务、子项、资产关联持久化，不按文件名恢复、认领或去重归属。
- 创建时持久化经过身份解析的 owner 与配额模式，冻结用于本任务的身份合同。对 owner/本地模式的合法豁免不能靠 rid 为空猜测；普通用户也不能因此漏账。历史任务身份无法证明则阻断维护，不能自动停止。
- 主任务幂等键按主体隔离。恢复同一任务不得重复创建对象、子项、转换任务或收费；重新上传是明确的新任务。
- 用户阶段统一为等待容量、上传、服务器接收、处理、可查看，以及取消/失败。处理阶段可说明解包/转换，但不暴露 SDK、锁、代次等实现细节。
- 100% 上传只表示传输完成。接口返回权威 task state、结果 slide IDs/子项结果、可否取消与可否重试；不以文件已经存在推断可查看。

### 3.2 内容处理与结果合同

先从 V1/V2 提取**与 Flask request 无关**的验证、包处理、转换受理、项目关联服务，再由 COS 摄取调用。不要从 worker 直接调用旧 HTTP view 或构造伪 request。

| 输入 | 统一处理与结果 |
|---|---|
| 原生单文件 | 下载固定版本，可信大小/内容校验，单 slide 发布 |
| ZIP 中单个 MRXS bundle | 使用已有安全解包和伴侣清单验证，以一个 bundle 原子发布；不能把伴侣文件各当一张 slide |
| ZIP 多切片 | 建稳定子项映射，复用现有 ZIP 的包失败/撤回语义；不得悄悄改成部分成功。U0 必须将现行行为及退款规则写成契约测试再迁移 |
| KFB/KFBF 等当前允许的转换格式 | 摄取源完成后交现有 conversion 作业，持久化源责任及结果关联；主任务跟踪到转换发布/失败，不提前显示可查看 |
| 裸 MRXS 或其他不完整 bundle | 保持明确拒绝并提示正确打包方式；统一 COS 不意味着取消格式安全限制 |

支持列表从现有格式注册表与解码能力派生，后端权威下发；不要再维护独立 `_COS_NATIVE_EXTS` 与另一套前端词表。新增接受形态必须有真实处理能力，不能只放宽扩展名。

ZIP 子项关系优先复用/泛化已有批量发布结构；若旧表强依赖 upload_tasks，新增最小 ingestion 子项关系及外键，而不是为每个包伪造一套旧上传任务。转换保留已有 conversion_jobs，传递明确的源任务/责任，避免两个独立任务同时自认为拥有同一容量。

### 3.3 取消、容量与清理

延续“租约决定执行，责任跟随任务”的模型：绑定预约不因 TTL 消失，续租不重新准入，released 不复活。普通上传和维护核账不得共用绕过配额的入口。

- COS 池按原始对象、历史版本、multipart 碎片责任管理；本地按源、解包/转换和最终资产的既有计量合同管理，两种资源独立释放。
- 大包解压/转换输出可能超过原始大小。复用安全解压的成员数/展开字节/路径/链接等限制，写下一段可能增加的字节前先补足本地责任；未知输出以有界块预算逐步补占，不可写完再补账。额度不足进入明确失败与清理，不留无账中间件。
- 同一源在 download→解包/转换→发布间交接，不可重复计算同 inode，也不可遗漏实际独立副本。每个责任的 owner、用途、持有者和结算点列入调用点清单，转交与旧执行者失效同事务。
- 文件写、首次 mkdir、移动、提升与删除沿用稳定任务存储锁；有子作业时明确源/目标锁键与固定锁序，不用父任务 ID 的一把锁冒充覆盖所有子作业。
- commit intent 已持久化后保持不可盲目取消边界。ZIP 有已发布子项时按原包撤回合同完成协调，转换失败按现有作业归属收口，不株连幂等复用的其他任务。
- 主任务终态不等于清理完成；清理意图、重试、确认与预约释放持久化并幂等。repair 必须同事务建立责任、绑定、可领取清理工作。
- 不减少现有 COS 的签名约束、可信 ListParts/版本核对、Range 校验、预算与 fail-closed 对账。浏览器文件重新选择不能只凭同名续传：核实同一文件身份，混合内容不得通过最终验证。

## 4. 前端、API 和不可用行为

新上传始终调用 `/api/ingestions`。继续复用官方 SDK 授权薄适配和现有 multipart 传输；首轮不为“小文件快一点”新增第二套单 PUT 授权协议。若协议对小文件存在最低边界，先用官方文档与测试核实再解决，不凭经验猜 SDK 行为。

- 删除大小分流、新上传 COS toggle、“改用平台上传”、`fallback_transport=v2` 和对应 i18n 文案。
- 前端从一个 capability 对象读取可用性、产品上限、格式与并发参数。capability off 时新 COS-only 构建禁用创建，显示上传暂不可用；不能因不可用悄悄启动 V1/V2。
- 超产品上限立即拒绝，不建任务/预约；合法大小但池余额不足返回持久等待和队列状态。配置根本不能接纳产品上限属于发布门禁失败，不是用户等待问题。
- 池暂停、月预算耗尽、网络故障、CSP/CORS 不通都提供稳定错误及恢复方式，不提供另一后端。重试和刷新沿用当前任务，不产生重复责任。
- 浏览器到 COS 的请求继续使用独立传输，不附平台 Cookie/CSRF；平台控制 API 保留会话与 CSRF。恢复信息不存凭证/签名 URL，签名仍按需获取。
- ZIP/转换结果前端按统一任务展示，项目关联按 slide ID，不再依赖旧上传响应 `name`。
- 盘点 HistoPilot、SDK、插件及脚本的真实调用方；用户上传调用方迁移到唯一控制 API。内部导入不因为接口名字包含 upload 就绕传 COS。旧客户端收到明确迁移错误，不能触发兼容新建路径。

## 5. 兼容窗口与退役方式

交付两个可构建的代码检查点，避免在未实际排空生产时假称旧链路已经退役：

**检查点 A：新入口统一＋旧任务排空版。** 切换部署后 V1/V2 停止新建。所有新任务走 COS；兼容代码只接受切换前已持久化的具体任务 ID，提供必要的状态、续传、提交恢复、取消与清理。兼容调用不得创建新旧任务或给失败旧任务换 ID 重开。

没有持久 ID 的 V1 在途请求必须在停写切换时结束或明确中止并核查残留，不能在新部署中“继续一次旧 POST”。旧 V2 页面只能恢复旧 ID；新建请求返回明确 410/migration code。

迁移模式须服务端明确为“排空版”或“最终版”，不要堆叠多个可任意组合的路由开关。不要依赖可被客户端提交的时间戳证明旧任务；以冻结任务清单/可信持久切换边界验证资格。

**检查点 B：最终退役候选版。** 删除旧 HTTP 字节接收、前端 V1/V2 transport、大小路由、对应配置与专属恢复/补偿。该版只允许在生产旧任务排空证明通过后部署；Agent 可先在副本中完成排空并构建 B，不伪造生产证明。

排空证明至少包括：

- 没有旧 active/committing 或未裁决 commit intent，没有旧请求/worker/子进程继续写入；
- 没有旧任务未释放的 reserved、待清理行、未解释暂存或未完成转换责任转交；
- 已发布资产、分享/项目关联及 used 结算一致；每用户 reserved 与责任行合计一致；
- 浏览器旧恢复记录能识别终态或失效，不会发起新旧上传；所有调用方迁移完成。

历史任务、已结算预约、迁移回执保留为只读审计数据，不要求为了删旧上传接口立即 DROP 表。若内部转换/批次仍引用旧表，先完成职责与引用迁移再删除模块；不得让新 COS 流程依赖最终计划删除的兼容入口。

## 7. Agent 连续执行顺序

### U0：基线、补缺与契约冻结

验证 R15 两条反例并修复仍存在的问题；扫描所有用户上传入口、内部来源、格式/大小限额、身份模式、任务/结果关系。先记录实际锁图和容量转移图。冻结现有 ZIP 失败/撤回与转换收费语义为测试，不在迁移时重新猜测产品规则。

产物：调用点/删除清单、格式×身份×大小矩阵、容量冲突计算、当前门禁结果。反例源码以 `.py.txt` 保存在文档目录；执行时放到 tests 使用现有 conftest，避免 pytest 收集文档副本。

### U1：提取处理领域服务

从 app.py 的 V1/V2 分支提取原生验证、ZIP、MRXS、转换受理和结果关联；暂时由旧入口调用新服务以验证行为一致。统一发布和财务 SQL 保持唯一。处理服务输入是任务/文件描述与身份，不是 HTTP request。

### U2：扩展 ingestion 格式与责任链

增加必要持久字段/最小子项关系及迁移，接通 ZIP/MRXS、转换和失败清理；完善主任务进度与多结果 API。迁移号选择下一个空闲号，不改已发布迁移文件。

覆盖父子任务取消/重试、源文件交接、commit intent 恢复、真实字节预算。单纯扩大 `_COS_NATIVE_EXTS` 或返回“交旧接口处理”不算完成。

### U3：前端和调用方统一

新任务只走 COS，删除选路 UI 与自动回退；补转换/包任务进度、排队、刷新与失败处理。迁移实际外部调用方，核实 HP 平台契约；没有调用关系的 HP 代码不为凑交付而修改。

### U4：形成检查点 A 与排空工具

实现旧任务只恢复不新建的兼容层、切换前只读预审/冻结清单、排空核验及报告。API 禁止客户端伪装旧 ID；报告未知/异常项 no-go。制作独立副本，演练旧任务恢复、失败、清理与重启，产出可复跑证据。

### U5：形成检查点 B，实际删除旧传输代码

以已排空的副本为验证输入删除第 6 节旧实现；保留检查点 A 的确切提交/构建信息用于先行部署。B 代码完成不等于生产已具备部署资格。新建、传输、错误提示与最终配置中不得残留隐式本地上传分支。

### U6：完整验收和交付

执行第 8 节；按仓库实际命令串行跑全量门禁，明确已知无关失败，不与 JS/HP 等重负载任务并行导致归因混乱。更新 inventory、COS 设计中的旧策略、部署 runbook、交付日志与新客户端接口说明。

最终报告提供两个检查点的文件/提交与构建方式、旧代码删除证据、测试命令/结果、成本与容量配置草案、待实际执行的生产门禁。不要将“还留 V1/V2 作为永久 fallback”写成完成，也不要在缺生产排空证明时直接部署 B。

| 尺寸 | 极小文件、分块边界±1、产品上限±1、池余额边界；不上传真实 10 GiB 测试数据也能测原子准入，真实吞吐验收另计 |
| 格式 | 所有现有允许原生格式、有效/损坏 ZIP、完整/缺成员 MRXS、ZIP 多项、KFB/KFBF；真实厂商样本单独门禁 |
| 内容 | 超长/截短/篡改分块、错 ETag/版本/Range、同名不同内容重选、压缩炸弹/穿越/链接、SHA 不符；沿用既有拒绝条件 |
| 生命周期 | 上传/下载/解包/转换中取消，worker 重启，Complete 响应丢失，commit intent 后崩溃；任务不挂死且不重复收费 |
| 物理与容量 | 晚到 writer 与清理互斥；本地/远端清理分别失败，责任保留；补占失败不继续写；清理确认后一次释放；队列被正确唤醒 |
| 路由退役 | 新用户界面无大小/后端切换；COS 不可用不发 V1/V2 请求；A 拒绝旧新建但可恢复清单内 ID；B 无旧字节接收路径 |
| 迁移 | 终态无 rid/pending 残留、账本多记/少记、intent 未解决、owner 豁免、未知目录、重复应用、清理后重跑；no-go 不写入 |
| 安全与部署 | 三 origin CSP/CORS 无 bypass，页面不泄露长期凭证，镜像 COPY/依赖齐全，运行库迁移兼容两个检查点 |

测试环境 dogfood 必须实际走注册→验证→登录→上传→进度→查看→删除。默认用受控测试邮件收件器捕获验证链接，不借用户报告假定 SMTP 已成功；真实 SMTP/真实桶验收无授权时如实列待办。注册相关他人修改不得顺手重写。

至少运行上传、COS、发布、ZIP/MRXS、转换、百度、删除、容量、核账与历史审查回归；然后完整 Python、`npm run test:js` 和受影响的 HP build/contract。用浏览器观察实际网络，证明小/大新文件都只有唯一控制入口与 COS 数据请求，而不是仅断言某个 helper 被调用。

## 9. 上线门禁与回滚

生产顺序：在线只读预审 → 批准维护窗口与容量预算 → 停止旧新建并等待/停止旧请求及子进程 → 备份与恢复验证 → 部署 A 并迁移/核账 → COS 真实桶与三 origin 验收 → 开放新 COS 上传并排空旧任务 → 排空证明通过 → 部署 B。

capability 开启前还需原 Phase 5 容量故障演练、生命周期规则/账单核对、真实 MRXS 样本及所有未关闭审查项通过。不得绕过 CSP 验收，不为测试默认写入生产凭证。

COS 故障时关闭新建/签名并保留必要查询、恢复和清理能力；这不是重新启用 V1/V2 的回滚开关。回滚代码必须理解当时任务 schema、holder 与锁协议；需恢复旧数据结构时按已验证整套备份流程执行，不能把新任务交给不认识它的旧 worker。
