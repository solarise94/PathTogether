## 3. 实现裁决：不要在此重新选择方案

### 3.1 文件写入与清理共用稳定任务锁

在现有存储层或一个小的 `task_storage_lock` 模块实现 Linux 跨进程 `flock`。锁路径采用 `UPLOAD_DIR/.task-locks/<kind>/<task_id>.lock`，kind 为固定枚举、ID 用现有安全组件校验。锁必须在 `.staging` 树之外；不能删除锁所在 inode 后继续使用同任务 ID。

- 任务所有 mkdir/open/write/truncate/rename/adopt/promote 操作，以及清理全部 generation 的操作，共用这把锁。不能只包 `pwrite`，否则“清理完成后首次建目录”仍会发生。
- writer 获锁后从 DB 重读任务状态、owner/holder、generation/token、执行期限；验证成功才做文件 I/O。claim 阶段读过一次不算。写入后的 checkpoint 仍保留原 DB fencing。
- 文件句柄必须在释放锁前关闭。外部转换子进程写入时，父进程持锁到子进程退出并确认不会继续写；父进程崩溃的子进程存活情形也必须有机制约束，不能假定取消 DB 状态会停止子进程。
- 已有 V2 `.staging/<id>/chunk.lock` 用新锁替换，不并存两套互斥机制。引用同任务的所有进程须看到同一个 UPLOAD_DIR 和锁目录；若部署文件系统不能保证 flock，则该部署不满足本方案，不能回退到仅 DB generation 检查。
- 正常运行不 unlink 锁文件。维护清理只在全部 API/worker/子进程停写、无人持锁或等待时进行；将锁目录排除出资产与暂存容量扫描。锁文件是协调元数据，不是待删上传内容。
- 不做隐式可重入锁。持锁流程调用明确的内部 `*_under_storage_lock` 操作；内部只能记录待清理，退出最外层锁后再调用清理入口。避免 `_fail → fail_job → cleanup → 再次 flock` 自锁。不要用进程级布尔值声称当前线程已经持锁。

### 3.2 统一顺序：文件锁在外，短 DB 事务在内

writer 顺序：claim 短事务提交 → 获取文件锁 → 短事务重验任务 → 文件 I/O → 短事务 checkpoint/发布结算 → 关 fd → 释放文件锁。

取消/超期顺序：短事务置终止及清理 pending → **提交并释放 DB 锁** → 获取文件锁 → 短事务重验清理资格/token → 删除任务树 → 短事务释放责任并完成清理 → 释放文件锁。

这里允许已进入临界区的旧 writer 先结束；它结束前容量始终保留。等待文件锁超时的请求可以返回已接受清理，持久重试继续处理，不把超时当删除成功。

锁序约束：

1. 任何 DB 行锁/事务级 advisory lock 持有期间，不得等待文件锁。
2. 持文件锁时，沿用各通道既有发布锁序，财务部分仍是 task/job → quota → reservation；完整锁图包含 slide advisory、slides、批次和 pool。
3. 同一操作尽量只取一个任务文件锁；确需跨任务操作，按 `(kind,id)` 排序并去重，不能出现持 A 等 B / 持 B 等 A。
4. 不在 DB 事务内执行网络等待、文件树删除或等待子进程。
5. 清理只能在文件锁内完成“确认静止 → 删除 → DB 收口”；不能先删树，再另起锁区间释放预约。

发布 commit intent 的不可取消边界保持原合同。核验阶段与正式发布可能有不同 DB 锁，但不能出现间隙允许清理与提升操作交错。

### 3.3 清理收口使用同一事务

COS 本地清理重验任务允许清理、pending/failed 状态以及预期 token/generation 后，释放对应预约并标 cleaned；重复执行幂等。远端清理继续使用原独立 token 与池释放合同。

V1/V2 的 `_upload_v2_cleanup_confirmed` 当前先 `clear_cleanup_pending`，再独立尽力释放。改成一个 store 事务：锁 task → quota → reservation，释放责任与删除 pending 同事务。DB 收口失败保留 pending，不能删掉重试记录后只记日志。这是统一清理协议必需的调用方收口，不额外建清理队列。

失败登记必须持久可重试。旧 writer 的迟到状态冲突正常退出；不要用宽泛吞异常掩盖真实 I/O 或数据库错误。

### 3.4 核账只补责任，不恢复执行

删除脚本中把所有异常任务改回 `active/uploading` 的逻辑。本轮不实现损坏任务自动续传：那需要独立验证远端版本、checkpoint、commit intent 和足额执行预算，不属于补记残留的职责。

新 CLI 用 `--repair-residuals` 表示“按冻结证据补记残留责任”。旧 `--reattach` 显式报参数错误并提示替代参数；不得悄悄保留会恢复执行的旧含义。同步更新文档和测试。默认 dry-run，写入必须显式 `--apply`。

- 正常、绑定一致的活跃任务不改变状态。
- 缺失/released 责任的异常任务先停执行，按真实残留补建责任，任务保持失败/取消与清理 pending；不得新发签名、下载、上传或发布。
- 本地清理与 COS 远端清理责任独立保留。核账本身不删除任何本地/远端数据，不调用清理 worker。
- 有未解决 commit intent、consumed 记录却无法证明结算、跨 owner/holder、共享预算归因不明时，阻断并输出核查项，不强行置 failed 或自动扣第二次 used。
- owner/本地模式等配额豁免按身份合同明确识别，预约为空不等于异常。普通用户也不能靠 rid 为空获得豁免。

### 3.5 维护专用补记，不暴露绕过准入的参数

拆出维护专用 `record_reconciled_residual_locked`（名称可按风格调整），与正常准入共享底层唯一财务记账实现，但不执行“新上传”的额度、并发、小时次数判断。

调用前提是受信维护计划、已停止的任务、已复核的路径和字节证据。该入口只供核账脚本调用，不放进 Web API；正常 reserve 接口不能靠用户或普通调用方传 `origin='reconcile'` 绕过门禁。

补记仍按 task → quota → reservation 加锁，写 `origin='reconcile'`，旧 released 行保持不变，新责任及任务/pending 指针同事务更新。容量不足也按实补记，quota_bytes 不变；超额用户的新准入仍由原 guard 拒绝。

如果 quota 原本已计入某笔无法解释的责任，不能简单再加一次。计划必须先解释“原 reserved 汇总、账本余额、将绑定/补记的责任”的差异；解释不全则 no-go。consumed 不作为缺失预约自动补记，先核对已发布资产和 used。

保留 `upload_reservations` 为唯一容量责任表，不新增第二套容量账本。

## 4. 核账工具的完整合同

### 4.1 扫描集合与字节证据

以任务表、预约表、清理表和任务存储目录做双向核对，集合至少包含：

- 活跃上传/COS/百度批次及其预约；
- 所有终态任务的 pending/failed 清理工作；终态却缺清理记录的已知残留；
- 无有效任务引用的 reserved 预约，以及 task 指向与 holder 反向指向不一致的记录；
- ZIP/百度子项与批次共享预算、转换的源/产物关系，不把批次 ID 根目录当作全部子项所在路径；
- 已发布资产、consumed 记录与暂存硬链接的关系，避免把已计实占的同一 inode 重复补账。

逐责任检查 owner、holder_kind/id、purpose、状态、计量依据、任务/清理双向引用。未知目录单列阻断，不能因找不到任务就自动删除或忽略。

替换 `_staging_bytes` 的“ValueError/OSError → 0/continue”：无法完整枚举或读取就是证据不完整、no-go。拒绝路径逃逸和符号链接越界；文件消失、成员变化、类型变化均使冻结证据失效。复用现有文件审计工具，清单包含相对路径、类型、size、sha256；物理责任计量正确处理同 inode 硬链接，不能以压缩包声明大小或未经校验的客户端大小代替。

### 4.2 冻结计划、应用与重跑

新增明确的 `--plan-out` 和 `--plan` 工作流，具体 argparse 风格可沿用项目习惯：

1. 在线 dry-run 仅预审，不是可应用计划。
2. 维护窗口停写并停止旧 API/worker/重试器/相关子进程，备份；生成带 schema/工具版本、数据根身份、必要 DB 前态与文件清单的冻结计划。数据库口令、邮件配置、COS 密钥、分享 token 不进入证据。
3. `--apply --plan ...` 全量预检计划、文件证据与 DB 前态；发现一项无法解释的记录先 no-go，不边发现 mismatch 边提交前面的修改。文件锁只保证单任务互斥，不能伪称拿到核账脚本锁就证明所有外部 writer 已停止。
4. 文件扫描/哈希在 DB 事务外完成。维护停写成立后，在短事务内重读/CAS DB 前态，执行绑定、必要停止、补记、pending 更新及应用回执。
5. 应用后重新 collect/verify，并输出应用后的 over_quota、pending 和阻断项。不能继续输出应用前的快照作为终验。

幂等不能只依赖“任务已经不是 active 所以下次扫不到”。用持久 action key 标识每个计划动作，并同事务写回执。复用合适的已有维护回执结构；若没有，新增小表 `upload_capacity_repair_receipts`（action_key 唯一、plan_hash、目标类型/ID、动作、结果 rid、应用时间），仅作审计/去重，不存第二份容量余额。迁移编号选择下一个空闲号，不修改已发布 0072。

同计划重跑检查回执和已完成结果，不重复收费。清理完成之后重跑旧计划不得重新制造责任。无回执且输入漂移应拒绝；不通过伪造 reserved_at 或修改历史 released 行实现幂等。

退出码固定并入测试：0 表示检查完整且无未解释责任；2 为参数/环境错误；3 为证据缺失、漂移、mismatch 或未处理责任。已补记并可解释的超额可返回 0，但必须列出超额与“继续禁止新准入”；预约缺失但仍有未补记残留不得返回 0。

## 6. 验收矩阵与测试约束

| 用例 | 必须验证的最终不变量 |

| COS claim 后、首次建目录前取消 | 晚到 writer 获文件锁后重验并退出；cleaned+released 时无残留 |

| 目录无法读取、成员/内容漂移、未知残留 | no-go，不能低报为 0；不应用不完整计划 |
| 批次子目录、ZIP 部分完成、硬链接已发布源 | 真实路径与计量正确，责任不漏不重 |
| 应用中断、同计划重跑、清理后重跑 | action key 幂等，不再次绑定/补记已释放历史责任 |
