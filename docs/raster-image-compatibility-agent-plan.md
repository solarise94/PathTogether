# BMP / JPEG 普通图片统一兼容：Agent 实现任务书

日期：2026-09-15

状态：待实施。本次仅编写文档，前序探索性代码和测试改动已全部撤回。本文不是已实现功能说明，也不代表真实样本验收通过。

## 1. 目标与范围

为 `.bmp`、`.jpg`、`.jpeg` 增加统一普通图片适配，让它们通过现有上传、导入、查看、缩略图、瓦片及允许的像素标注流程使用。

核心语义：这些图片缺少的通常是物理标尺，并非坐标。以校正方向后的图片左上角为原点，使用 level-0 像素坐标；没有可信校准时，不生成物理尺寸或扫描倍率。

实施边界：

- 复用 `open_slide(path, *, format_hint=None)` 和现有 HTTP 接口，不新增一套 BMP/JPEG 专用上传或查看 API。
- 首期支持单帧 BMP/JPEG。PNG/WebP/GIF、多帧图片、超大图磁盘金字塔转换作为后续扩展，不因 Pillow 能打开就自动放行。
- 保持 SVS、TIFF/OME-TIFF、MRXS、KFB/KFBF 的现有分流及能力语义。
- 不改上传运输策略，不自动扩大 COS 等独立运输通道的格式范围。
- 不在本任务中实现持久化人工标尺系统或修改分享权限策略。
- 后续 agent 被要求按本文实施时，可完成代码、测试和本地验证；本文不包含部署、发送通知、修改线上兼容请求状态的任务。
- 先检查工作区差异，保留已有改动。不要重置或顺带修改其它任务文件。

## 4. 实现合同

### 4.1 格式能力与入口

- BMP/JPG/JPEG 使用 `native-single-file`，`canonical_ext=null`；公开目录使用 `import_mode=direct`、`bundle_required=false`、`selectable_for_upload=true`。
- JPG/JPEG 是同一解码格式的别名，扩展名判断不区分大小写。
- 逻辑后缀和实际字节都校验。伪装成 BMP 的 PNG/TIFF 不因解码库支持而通过；JPEG 字节可用于 `.jpg` 与 `.jpeg`。
- `.part` 上传暂存文件必须由 `format_hint` 指定逻辑文件名，字节始终从实际暂存路径读取。保留 URL、NUL、目录和未知后缀的既有拒绝规则。
- 主站上传、V2 提交、ZIP 成员、本地导入使用同一能力判断和读取验证，不仅更新浏览器 accept。
- 用户文案说明“普通图片、支持像素坐标、无物理标尺”，不要展示解码库、reader 等内部实现词汇。

### 4.2 读取器与资源所有权

建议新增 `raster_slide.py`，通过 `slide_io.open_slide` 延迟导入。优先评估已有 `openslide.ImageSlide` 的包装能力，避免重写区域裁剪和 Deep Zoom 数学。

必须满足现有消费者使用的接口：

```text
properties / dimensions / level_count / level_dimensions / level_downsamples
get_best_level_for_downsample(d)
read_region((x, y), level, (w, h)) -> RGBA image
get_thumbnail(size)
associated_images / color_profile（按当前消费者需要提供）
close()
```

- 单层图片允许 `level_count=1`，由现有 DeepZoomGenerator 产生查看层级。
- 首次打开完整解码，截断文件应在提交提升前失败；不能只检查文件头就算验证成功。
- 读取器持有解码后图像，不逐瓦片重复打开/解码文件。灰度、调色板及 CMYK 转显示 RGB，验证颜色结果和 ICC 处理，不默默丢掉 profile 后假称色彩准确。
- BMP 若带 alpha，明确白底合成策略，保证缩略图和瓦片相同；越界区域仍遵循 OpenSlide 的透明 padding 语义。
- 使用 ImageSlide 包装 PIL 图片时，核实图片所有权；包装器关闭不一定关闭传入的 PIL 图片。正常退出、构造失败、重复 close 都不能泄漏源文件、像素缓冲和中间图像。
- 不修改 Pillow 全局开关来容忍截断文件或禁用解压炸弹保护。

### 4.3 方向与坐标

- JPEG 按 EXIF Orientation 校正后建立统一坐标系，覆盖旋转和镜像方向；宽高以校正后结果为准。
- 校正仅影响读取后的表示，保留原始上传字节和 SHA-256。
- info、DZI、缩略图、区域读取、标注保存/重开、截图和使用共享读取器的 AI 裁图都以这一坐标系为准。
- 不再由前端或下游第二次应用 EXIF；用户交互旋转/翻转仍是查看变换，不改持久化像素几何。
- 若生成任何磁盘派生图，沿用资产换代规则；方向/颜色处理策略变更时检查缓存版本，禁止同一缓存身份对应不同坐标结果。

### 4.4 元数据、物理标尺和分享权限

普通图片默认返回现有字段，不需要新增 HTTP API：

```json
{
  "width": 1920,
  "height": 1080,
  "mpp_x": null,
  "mpp_y": null,
  "objective": null,
  "mpp_source": "missing"
}
```

上面的宽高仅为示例。BMP/JPEG 的 DPI、EXIF 分辨率不能当作组织的 µm/px，不补默认 0.25 MPP 或 40×。

- 没有 MPP 时，保留像素尺寸、像素标注和缩放百分比；物理单位操作应禁用或明确说明缺标尺。
- 检查 UI 是否默认选中 mm，普通图片首次打开应能直接进入允许的像素操作，不要求填写虚假标尺。
- 已有 `setMpp` 更新的是前端状态，不能据此宣称服务端或分享页已获得持久化可信校准。
- `share_server._reject_preset_rect_mm` 会拒绝缺可信 MPP 的毫米预设标注，此规则必须保留；不能自动把 `preset_only` 分享改为自由像素标注。
- 为普通图片明确无可信标尺的限制提示，避免现有“在主站校准后重试”文案暗示本次已提供持久化校准。查看不受该预设标注限制影响。
- 像素标注仅在原有角色、授权和分享策略允许时开放；不扩大原有访问权限。
- 不改变历史 `size_mm` 的存储兼容约定，但前端不得把“未知”的占位数值展示成真实 0 mm 测量。

### 4.5 错误契约

- 使用 `SlideValidationError` 及既有稳定机器码，保留各上传路由当前状态码和终态清理语义。
- 不支持的逻辑后缀、真实格式不符、明显无效字节归 `invalid_slide`；解析/IO 失败归既有分类，截断文件稳定失败且不能提升为可用文件。
- 资源限制拒绝要有明确、可测试的原因；优先兼容既有外层码，若需要新增子原因字段，同步定义路由和前端处理。
- 客户端不得收到服务器绝对路径或底层异常堆栈；后台日志可以记录异常类型与格式。
- 验证失败不留下可见资产，不泄漏配额预占，临时文件遵循现有 V1/V2 清理约定。

### 4.6 内存与性能

普通图片不是可按需读块的金字塔切片。RGB 常驻缓冲约为 `W × H × 3`，方向校正、颜色转换、缩放和原图解码会额外占用内存，不能把文件大小当解码预算。

- 现有每张切片的句柄池默认允许 6 个句柄。普通图片起步采用每张图片每进程最多一个解码句柄，并保留借还锁与换代语义。
- 单句柄限制不能解决多图片、多进程总内存问题。检查现有缓存是否淘汰长期空闲图片；若没有，增加有界普通图片缓存预算或淘汰机制，不能只记录风险就声称内存有界。
- 在完整解码前检查宽高、像素数、帧数；限制应由共享策略提供，目录和错误文案一致。
- 像素上限和缓存预算由实测及目标进程内存决定，记录选值依据。此前讨论的“4000 万像素”不是已冻结需求。
- 记录冷打开、首张缩略图、首张瓦片、并发请求和多图切换的峰值 RSS/耗时。报告环境、图片尺寸、进程数和并发数，不能只给一个缺上下文的时间。
- 超限应明确拒绝，后续再做后台磁盘金字塔；首期不自动进行无预算的大图转码。

## 5. 推荐实施顺序

1. **基线与样本**：检查 Git 差异、调用链、解码库和测试环境；能访问样本则核对摘要。确定内存方案及可测的限制。
2. **读取器**：先完成完整解码、真实格式约束、EXIF、颜色、区域读取、资源释放及直接 Deep Zoom 测试。
3. **注册与上传**：统一格式词表，接入 V1/V2、ZIP、本地导入和目录；验证 .part 提交及失败清理。
4. **查看与缓存**：接入主站/分享页，完成单句柄、缓存预算/淘汰、换代和方向一致性。
5. **产品语义**：像素操作默认值、缺 MPP 提示、物理预设限制、前端 accept/fallback 和本地化文案。
6. **验收与交付**：运行相关回归并报告真实样本状态、资源数据、剩余限制。完成本地实现不等于上线或请求已解决。

不要只改白名单后交付；读取器、入口、坐标语义、资源策略和主站/分享验证必须形成完整闭环。

## 7. Agent 交付格式

最终交付说明应包含：

1. 修改文件和统一入口如何接线。
2. 支持的 BMP/JPEG 子类型、像素上限、缓存预算及选值依据。

6. 已知限制和后续事项，尤其是持久化人工校准及超大图片转换。
