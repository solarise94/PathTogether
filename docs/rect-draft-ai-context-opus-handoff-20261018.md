## 3. 框选故障：已经确认与尚未确认

用户澄清：不是点击保存后报错，而是“点不到，框一直跟着鼠标走不能正常结束”。

已确认：

- 在真实 Chromium、真实前端、Flask 和内嵌 PostgreSQL 上，普通放置、移动、松开、点击浮条保存可以成功，POST 返回 200。
- 在无物理标尺的 BMP 上也能复现：拖动临时 ROI 框时丢失指针捕获，随后在框外松开鼠标，再把指针移回框内，框仍随**未按键的鼠标**移动。
- 复现日志中 `lostpointercapture` 后的 `pointerup` 落到 `anno-canvas`，没有落到 `roi-box`。后者的 `dragInfo` 因而未被清理。
- 一次记录中松开时屏幕框位置约为 `(836.95,460.98)`，之后仅悬停移动，框变成 `(905.86,495.44)`；宽高未变。

尚未确认：

- 用户那次真实操作究竟为何丢失释放事件/捕获：浏览器焦点、远程操作、OSD 捕获竞争，或其他路径，需要继续定位；当前不能断言已经完整复现用户设备上的全部卡顿。
- 独立的渲染性能瓶颈尚未做 CPU/frame trace，不能把“卡顿”全部归因于同一处，也不能声称已解决性能问题。
- JPG 格式本身出错没有证据。其他格式上同样存在该交互缺陷，说明转换 JPG 不能代替修复拖拽状态机。

### 3.1 代码位置与缺口

PathTogether `static/app.js`（以下行号对应上述基线，以函数名为准）：

- `onRoiPointerDown/Move/Up/Cancel`：约 3468–3568 行，临时框内部移动及边角缩放。
- `onRectCanvasPointerDown/Move/Up/Cancel`：约 3579–3701 行，初始画框与预设点击放置。
- `exitRoi`、`discardRectDraft`、`onRectKeydown`：工具退出和撤销。
- 画布监听器：约 14000 行。

当前缺口：

- ROI 仅监听自身的 `pointermove/up/cancel`，没有真正绑定 `lostpointercapture`；尽管注释写了“丢失捕获”，行为并未覆盖。
- move/up 没有校验活动 `pointerId`，也没有阻止 `buttons === 0` 的悬停继续更新几何。
- 画布矩形绘制同样没有捕获丢失处理。
- 退出/撤稿未完整清理活动拖拽；窗口失焦也缺少矩形拖拽的收尾。

### 3.2 建议实现要求

- 每次拖拽只归属于一个活动 pointer，忽略其他 pointer 的 move/up/cancel；不以右键/中键开启 ROI 拖拽。
- 正常 `pointerup`：保留完成的几何，清理状态、监听器及捕获，恢复导航，刷新尺寸和浮条；初始自由画框仍沿用已有“松开自动保存”行为。
- `pointercancel`、`lostpointercapture`、窗口失焦：结束活动手势，按现有取消语义恢复拖前几何，不触发保存。草稿本身仍可继续编辑或手动保存。
- move 发现按钮已松开：立即终止陈旧手势，避免 hover 改写几何；不要把这条兜底当作一次有效自动提交。
- **先清空会话状态，再 releasePointerCapture**，避免正常释放触发丢失捕获回调后错误回滚，或取消函数重入。
- 退出工具、Escape 撤稿、切片切换、ROI DOM 删除时清理手势；多次调用应安全。校验旧事件不会落到新切片或新草稿。
- 如果捕获申请失败，确保仍有可靠收尾，不能留下只能依靠 ROI 自身接收 pointerup 的拖拽；可选择 document/window 范围监听并在结束时移除。
- 处理完状态机再实测性能：拖拽期间是否每个事件触发完整 OSD 瓦片重绘、强制布局或重复创建浮条；仅在有证据时合并到 animation frame，结束/取消时必须处理最后一帧，不能留待执行的旧回调。

### 3.3 验收

- 真实 JPG（含无 MPP）与另一格式各测：预设放置、框内移动、四边/四角缩放、松开后跨过框与按钮，框不再跟随；保存后刷新，几何一致。
- 捕获丢失 → 框外松开 → 再悬停；鼠标释放事件缺失但下一事件 buttons=0；窗口失焦后返回；其他 pointer 事件；取消后立即重新框选。
- 初始画框捕获丢失不保存，恢复旧草稿或空状态；正常自由画框仍只自动保存一次。
- 未保存草稿、已保存标记编辑、缩放平移与旋转、AI 浮条点击不能相互抢事件；真实浏览器检查而非只做源码正则断言。
- “不跟手”另录性能 trace，并在普通及较慢 CPU 下观察拖动。修复报告必须区分状态机验证与性能验证。

## 4. AI 现状：两套入口并存

### 4.1 当前“让 AI 解读”已经是附件链路

PT `openAnnoToolbarMenu` → `freezeMarkerAttachPayload` →
`emitConversationAttachIntent` → `conversation.attachIntent`。

HP `integrations/pathtogether/ui/main.js:pushPendingAttach` 消费它，打开 AI 面板、追加附件；
`intent="interpret"` 只在输入框为空时预填问题，不创建 fork，也不自动发送。

因此，现有菜单项不需要另造一个解读服务；问题主要是入口太深、名字像立即执行。

### 4.2 独立 fork 小解读确实还在

- PT `buildAnnoAiActions` 仍渲染“快速问答”与“从此处深读”，分别发 `fork.open`、`branch.open`。
- HP `integrations/pathtogether/ui/main.js` 注册两个桥处理器。
- HP `integrations/pathtogether/ui/sessions.js`：`openForkChat/sendForkQuestion` 使用 `/api/ai/ask`；`openBranchFromAnno` 使用 `/api/ai/branch`。
- HP `src/server.ts:handleAsk`、`src/agent-runner.ts:askFork/driveFork`、`src/prompts.ts:FORK_LITE_SYSTEM_PROMPT` 仍有独立会话实现。
- lite fork 使用单独的受限提示词且无工具；branch 是另一种有完整工具集的分支，不应在审查时与 lite fork 混为一谈。

### 4.3 已有可复用的目标上下文

HP `src/agent-runner.ts:withSelectionContext` 已将 `skillRequest.target` 的 roi/annotation 作为“发送时选中”注入上下文，明确不限制工具使用。
另有 `withAttachmentContext`、`applyAttachmentImageRefs`，可承载用户显式加入的冻结附件。

需注意：HP UI `applyPendingAttachesToBody` 当前把最后一个附件 bbox 同时写为 `body.viewport`。
这会将“用户加入的目标”和“当前视野”混在同一字段；统一方案应分别表达，不能仅靠改按钮名称。

## 5. 建议交互与上下文契约

### 5.1 浮条与名称

- 人工/AI 已保存标记：`[接受（仅待复核）] [编辑备注] [✨ 加入 AI 对话] [⋯]`。
- “锁定位置/解锁位置”移至“⋯”，保留锁状态提示；只读对象不能修改锁。
- 只读且有权查看的标记也应可加入对话，不能误用 can_edit 限制讨论。
- “⋯”中的定位动作建议叫“居中显示此标记”，tooltip 写“调整视野并高亮此标记”；它只导航，不加入上下文。
- “加入 AI 对话”打开当前 AI 面板，在当前会话草稿中加入目标卡，聚焦输入框；不跳到另一会话、不发送、不启动模型、不覆盖已有文字。
- 建议取消 interpret 专属预填，用输入框 placeholder 提示“针对已加入的标记提问…”。添加附件本身不代表用户已经提出“解读”请求。
- 插件未就绪或几何不可用时显示明确原因；缺少权限不能假装添加成功。
- 未保存候选框优先保留“保存为标记”；如要提供加入对话，作为 ROI 附件，不伪造 annotation_id，也不悄悄落库。可在后续独立扩展。

### 5.2 本轮目标是上下文，不是围栏

优先复用现有附件协议与 target 适配，避免建立第三套选择/快照链路：

- 用户点击时冻结切片身份、标注 ID 与 revision、几何/bbox、render context；多个目标全部保留，并可移除。
- 自动读取的“发送时选中”、显式加入的附件、实时视野分开表达；显式目标点击加入后，后续移动视野或选中别的标记不能悄悄替换它。
- 发送保留当前对话历史、已有摘要、全片信息及正常工具集。提示“本轮用户关注这些目标，可结合上下文及其他视野判断”，不要求只看该区域，也不强制某个工具。
- 优先审查现有 `withSelectionContext` 的复用方式，别为了普通提问强制套一个无关 skill；别让 skillRequest.target 与附件各自重复注入同一个目标。
- 附件范围是证据来源；实时 viewport 独立表示浏览器视野。去掉“最后一个附件覆盖 viewport”的混淆时，必须同步审查网关、sidecar 和旧客户端兼容。
- 每个目标的图像证据必须真实进入请求组装，不能只追加 ID/坐标文字；多个目标不能最后只剩一张图。
- 卡片中文案显示为用户选择的数据；标注 note/label 不应变成系统指令。
- 继续复用当前身份、会话、切片及 revision 校验；发送失败保留草稿，接受后仅消费本次附件；重试不重复追加图像/用户消息。
- 切片、账号或对话切换后不能把前一处的目标自动挂到新位置。标注更新/删除时明确提示刷新附件或移除，不能默默用另一 revision 替换。

### 5.3 fork 退役步骤

1. 移除 PT 标注列表以及 HP 自身重复渲染的“快速问答”入口，统一到“加入 AI 对话”。同时移除从标记隐式新建 branch 的“从此处深读”入口，避免继续保留两种相近的新建路径。
2. 为旧 `fork.open/branch.open` 桥调用设置有期限的兼容适配：解析并校验标记后，加入当前普通 AI 对话草稿，不自动发请求。不要只删一个可见按钮，留下历史卡片/其他视图还能新建。
3. 历史 fork/branch 的会话文件、消息、索引和引用保留。旧 fork 可查看，并提供显式“在 AI 对话中继续”；需要继承历史时，进入普通会话时带入有来源标识的历史摘要/必要证据，不默默清空，也不静默改写旧会话 kind。
4. 历史 branch 的查看/续聊按已有完整会话语义保留；停止新建标注专属支线不等于删掉其历史或强制改格式。
5. 新 UI 与兼容桥到位后，单独关闭旧 /ask 新建能力并返回可识别的退役原因；不要使用和“根标注已删除”无法区分的笼统错误。branch 新建与历史续聊要区分处理，不能一起封掉。
6. 最后清理无调用的 fork prompt、runner、配置和测试。历史读取与会话索引兼容保留到有明确迁移方案时；本次不批量迁移/删除会话。

## 6. JPG 存量兼容转换的处理建议

本次不把批量转换作为修复前提。若交互修好后仍有特定 JPG 的读取问题：

- 先做只读盘点：文件头实际类型、解码错误、宽高、EXIF 方向、颜色、MPP、当前 reader 的结果；对问题样本复现后再选转换路径。
- 先处理个别确认失败的样本，保留原文件与可回滚的派生版本。
- 转换前后必须保证或显式映射 level-0 坐标、方向、尺寸与 MPP；否则既有标注、AI 附件 bbox、分享链接可能错位。
- 不覆盖原图，不因生成 TIFF 就重新分配 slide_id；发布派生版本和缓存失效应走现有资产机制。
- “转换后 reader 能打开”不能当作标注/坐标兼容验证。没有证据证明现有 JPG 读取失败时，不做全库迁移。
