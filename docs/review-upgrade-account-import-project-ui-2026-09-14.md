## 1. 结论与优先级

截图对应的显示可以由正常的待激活用户触发，已经在隔离 PostgreSQL 中复现。后台把“尚未获得额度”和“已激活用户的额度记录异常缺失”混成了一个错误；桌面列表还隐藏了待激活提示。截图不足以确定目标账号的实际激活状态，需要按第 3 节只读核对。

百度分享目前是方案与 CLI 验证记录，当前应用没有对应的产品 API、任务存储或界面入口。新格式兼容申请和 KFB/KFBF 上传转换则已有工作区实现，需补可靠性与交互闭环。

| 编号 | 优先级 | 发现 | 证据级别 |
|---|---|---|---|
| R1 | P2 | 待激活用户被显示为额度缺失，桌面只突出“启用” | 隔离库真实注册/API 链路复现 |
| R2 | P1 | 格式兼容申请 JSONL 跨进程覆盖，可能丢申请或重复通知 | 双进程确定性交错复现丢记录 |

| R4 | P2 | 新建项目提交中无防重，连续确认发出重复请求 | 执行原前端函数复现两次 POST |

## 2. Review 发现

### R1：激活状态没有参与额度展示

证据链：

- `registration_store.py:935` 的 `_insert_pending_user_tx` 正常创建 `pending_activation` 用户，`disabled=false`、`ai_access=false`，不创建 allowance；邀请码激活事务才创建额度。
- `app.py:6924` 对用户列表全部普通用户调用 `admin_users_spend_summaries`，只传角色和 ID，没有传激活状态。
- `spend_store.py:1920` 调用 `total_allowance_summary_tx`；后者在 `:1945` 对缺行统一抛出 `SpendTotalAllowanceMissingError`。
- `plugins/pathtogether-admin/ui/main.js:1018`、`:1075` 原样展示错误码；`:1124` 将“待激活”写入 `.adm-stack-mobile`，该元素在 `ui/style.css:403` 默认隐藏，移动端规则才显示。

隔离库实测结果（省略测试用户 ID）：

```json
{
  "enabled": true,
  "activation_state": "pending_activation",
  "ai_access": false,
  "spend": {"error": "spend_total_allowance_missing", "spend_target": "total_allowance"}
}
```

这说明无需数据库损坏就会触发截图同类显示。`enabled` 只表示没有被禁用，不表示完成激活或可以使用 AI。已有 `tests/test_admin_batch_d.py:557` 的“缺行即损坏”测试只覆盖已开通用户；其注释“正常路径造不出来”已不适用于新增的待激活注册流程。

**修复建议：**管理 API 增加明确的额度展示状态，例如 `not_provisioned / available / unavailable`；对合法待激活状态显示“待激活，激活后发放额度”。保留已激活用户缺行错误，不在读接口自动创建额度。桌面和移动端都显示激活状态，并独立表达禁用状态、AI 权限；错误码放入技术详情。账户余额接口也应采用同一语义，并保持现有激活权限守卫。

验收：待激活、已激活且有额度、已激活但缺行、禁用、owner 月额度分别有明确状态；刷新列表不新增额度或审计写入；完成邀请码激活后额度只创建一次。

### R2：兼容申请的持久化锁只保护单进程

`format_request_store.py:42` 使用 `threading.RLock()`；`:63–119` 是“读全部 JSONL → 修改 → 写固定 `.part` → replace”，`:190` 邮件排水同样读后全量覆盖。`docker_entry.sh:152` 默认启动两个 Gunicorn worker，`:110` 起另一个格式申请邮件进程；POST 后还会调用进程内 `drain_async()`。

两进程同时读到旧快照，即便随后顺序写入，后写者也会覆盖先写者的新请求。本次让两个进程在读取后同步，再依次调用原 `_save_all`，得到：`exit_codes=[0,0], submitted=2, persisted=1`。该复现仅控制执行顺序，未改变读写内容。固定 `.part` 还可能产生互相替换文件的异常；多个排水进程没有跨进程领取机制，存在重复通知风险，这两项没有本次实发验证。

**修复建议：**沿用项目现有 PostgreSQL，将申请和邮件任务事务化；任务领取使用行锁/租约及领取者校验。提交返回稳定申请 ID，邮件发送完成时按领取凭证更新，发送结果不确定保持 `uncertain`，不自动重发。每日次数校验与申请写入需原子执行；样本保存后申请事务失败要清理孤立文件。迁移旧 JSONL 时备份、按申请 ID 去重，保留原状态，避免把 `sent/uncertain` 重新排队。

仅将 Web worker 数改为 1 不足以修复，因为独立邮件 worker 仍会并发读写。

验收：两个 Web 进程同时提交不丢记录；两个发送 worker 不重复领取；提交与排水并发不覆盖；崩溃后可恢复；已有 `uncertain` 不自动重发；发送通道关闭时申请仍能查询。

### R3：取消后新建项目仍夹带旧切片

`static/app.js:2212` 关闭/打开表单只处理可见性和文本，没有清空 `pendingNewProjectSlides`。`:2219` 把显式空数组也视为“回退到旧选择”；`:5291` 取消只隐藏表单，`:5341` 附近的含选中新建设置持久选择。

复现步骤：勾选切片 A → “新建项目(含选中)” → 取消 → 顶部“新建项目” → 填名称并确认。执行原函数得到 POST `slides=["selected.svs"]`，用户期望的空项目仍包含 A。

**修复建议：**显式区分 `empty` 与 `selection` 新建模式。普通新建初始化空选择；取消清理当前草稿；显式 `[]` 必须表示空项目，不能按数组长度推导默认值。表单内持续显示“空项目”或“包含 N 张切片”，可展开核对和移除。

### R4：新建项目无提交中保护

`static/app.js:2219` 提交函数没有 in-flight guard，也没有禁用确认按钮；确认点击和备注输入框 Enter 都可以调用它。`app.py:17757` 与 `share_store_pg.py:1471` 每次创建随机项目 ID，无请求幂等键。

本次保持首个请求 pending，再调用一次原函数，记录到两次相同 POST。后端当前没有去重行为，因此慢网下双击可产生重复项目。

**修复建议：**点击和 Enter 共用提交锁，显示“创建中”；失败恢复操作并保留草稿，成功关闭并清空，自动展开/定位返回的 `pid`。如支持响应丢失后的自动重试，再增加按用户作用域的幂等键；同名项目是否允许应独立决定，不能用名称强行去重。

### R5：转换观察超时被当成任务失败

`static/app.js:4689` 的 `pollConversionJob` 在本地观察超过 15 分钟后直接标失败并移除进度行，而后台任务可能仍在排队或运行。非成功 HTTP 响应没有按 `res.ok` 分支处理；网络异常反复重试，最终也进入该假失败。`:4653` 在进入转换轮询前删除上传恢复项，转换 ID 只随当前调用保留，刷新后没有可见的转换恢复列表。

**修复建议：**后台状态决定是否失败；观察超时显示“仍在后台处理”，网络故障显示“暂时无法获取进度”，保留任务 ID。提供按当前用户列出进行中任务的 API 和 UI，刷新可恢复；401/403、404、暂时故障分别处理。失败详情展示可行动的原因和重试入口。

验收：模拟排队超过 15 分钟、短暂断网、刷新、服务端失败、权限失效，不能误报已失败或丢失可查任务。KFB 与 KFBF 均覆盖。

## 3. 截图账号的只读排查与处置

本次没有读取该真实账号的数据，不能将本地复现直接断言为该账号的生产根因。先在管理台“详情”查看激活状态与 AI access；必要时执行以下只读 SQL，将占位符替换为目标登录账号，避免把完整结果写入公开报告：

```sql
BEGIN READ ONLY;
SELECT u.user_id, u.role, u.disabled, u.activation_state, u.ai_access,
       u.created_at, a.allowance_id, a.limit_nano_cny,
       a.spent_nano_cny, a.reserved_nano_cny, a.source, a.version
FROM users u
LEFT JOIN ai_spend_total_allowances a ON a.subject_id = u.user_id
WHERE lower(u.login_id) = lower('<目标登录账号>')
   OR u.email_normalized = lower('<目标登录账号>');

SELECT u.activation_state, count(*) AS missing_count
FROM users u
LEFT JOIN ai_spend_total_allowances a ON a.subject_id = u.user_id
WHERE u.role = 'user' AND a.allowance_id IS NULL
GROUP BY u.activation_state;
COMMIT;
```

- **待激活且无额度：**正常业务状态，修复展示；通过原有激活流程发放额度，不人工补行。
- **已激活但无额度：**实际数据异常，优先排查建号/激活审计、历史迁移执行记录、导入或恢复操作、旧金额窗口及 hold。当前正常建号和激活使用事务创建额度，不能仅凭错误码归因于注册失败。
- **库中有额度而页面报缺失：**核对当前部署版本、API 中的 subject ID、连接的数据库和环境是否一致，再查响应；截图本身不能证明页面对应当前工作区。

`migrations/0032_user_total_allowance_single_track.sql` 只物化默认额度等配置，没有为所有历史用户回填总额度；历史用户依赖 `scripts/cutover_user_total_allowances.py` 的专门迁移。但该脚本处理所有 `role='user'`，并不按新的待激活状态过滤，**不得直接拿来批量修复当前截图问题**。确需修复已激活历史用户时，应先形成明确名单与余额来源，在隔离恢复库验证余额守恒、未结 hold、审计与回滚方案，再实施。

## 4. 百度分享：从能力验证补成产品入口

当前 `docs/baidu-share-ingestion-open-source-review.md` 记录过 CLI 只读枚举验证，也包含尚未验证项和不同阶段的描述；本次不重新断言第三方工具当前能力。对 `app.py`、应用 JS、模板、存储及 worker 代码检索，未找到百度分享集成。问题不能通过增加一个跳转按钮完整解决。

建议入口位于统一“导入切片”面板，提供“本地文件 / 百度分享”页签。百度连接器未配置时页签仍可发现，显示“尚未配置”及原因；配置完成才启用枚举操作。

建议交互：

1. 粘贴分享文本，单独提供提取码字段；解析出的链接/提取码冲突时提示用户修正。按钮用“读取文件列表”，说明不会转存或下载。
2. 展示枚举进度、目录范围及错误。结果支持路径/文件名搜索、格式过滤、分页与选择统计；目录不能伪装成单文件。
3. 候选显示名称、来源相对目录、大小、格式能力：直接导入、需转换、缺少配套文件、不支持。保留服务端候选 ID；用户选择后服务端重新核验候选归属。
4. 用户选定目标项目或“未归类”；确认页显示选中文件数、字节数、转换提示、可用配额。显式“开始导入”后才转存和下载。
5. 持久任务展示转存、下载、校验、转换、入库及清理状态，支持部分成功、失败重试、刷新恢复。只清理本批次拥有的平台转存副本，禁止扩大到原分享或其他批次。

建议新增接口（以下均为设计，不是已有接口）：

| 接口 | 用途 |
|---|---|
| `POST /api/remote-imports/baidu/enumerations` | 校验分享输入，创建当前用户的只读枚举任务 |
| `GET /api/remote-imports/baidu/enumerations/{id}` | 查询任务状态 |
| `GET /api/remote-imports/baidu/enumerations/{id}/candidates?cursor=…` | 分页查询服务端候选 |
| `POST /api/remote-imports/baidu/imports` | 提交枚举 ID、候选 ID、目标项目、幂等键 |
| `GET /api/remote-imports/baidu/imports/{id}` | 查询批次与逐文件状态 |
| `POST /api/remote-imports/baidu/imports/{id}/cancel` | 请求取消，返回实际可取消状态 |

后端需要持久枚举/批次/条目记录、worker 租约、账号连接状态及幂等收口；复用现有格式判断、配额预占、内容校验和转换服务，不能直接把远端文件路径当成已导入切片。所有接口按当前用户授权，写接口沿用 CSRF，外部程序使用参数数组；分享文本不参与执行或自动元数据指令。大目录设置分页、超时、候选上限；过期枚举在导入前要求重新核验。

验收：嵌套目录、大目录分页、提取码错误、链接过期、目录读取不完整、空候选、混合 SVS/TIFF/KFB/KFBF、不完整 MRXS、越权候选、配额不足、双击导入、断网/服务重启、部分失败及本批次清理。枚举未完整成功时不能静默把部分结果称为完整列表。

### 5.2 格式能力与申请

当前 `_app_shell.html:225` 已接受 KFB/KFBF；`app.py:256` 内容探测、上传收口及 `conversion_worker.py` 已有转换分支，不能继续照抄注册表中 KFB“尚未接入上传”的旧 notes。`.ome.tif/.ome.tiff` 可落到 TIFF 后缀判断，界面应清楚标注 OME-TIFF；扩展名可选不等于任意内容均可成功读取。

建议将格式注册表输出为受控的前端能力数据，包含展示名、扩展名、导入方式、配套文件要求和限制。修正过期 notes 后再用于产品文案。KFB/KFBF 显示“上传后后台转换”；MRXS 显示需要完整包及打包指引。

“其他格式请求兼容”改为“申请新格式支持”：默认展示格式/扩展名、来源设备或软件、简短说明；联系邮箱与样本为可选。添加持久可见的字段标签，不能只有 placeholder。样本字段显示服务端配置的上限（当前默认 64 MiB）、用途及受控访问说明；前端预检查大小，后端仍权威校验。

提交成功显示申请编号和“已登记，等待评估”，区分登记成功与通知发送状态；目前 `static/app.js:5325` 成功后直接清空隐藏，未展示返回的 `request_id`。增加当前用户可查询的申请详情/列表，管理员工作台可处理和变更状态。202 不能被描述成“已经兼容”或“管理员已收到邮件”。

### 5.3 新建项目

使用独立弹窗或抽屉：项目名称、备注、初始切片三块。主按钮用“创建项目”；空项目提示“创建后可导入切片”，含选中模式展示 N 张及可移除清单。项目内和未归类切片共享勾选状态，界面必须解释实际纳入的集合，避免只显示“未归类”却带入项目内已选切片。

处理 R3/R4 后，补齐字段错误就地显示、提交中状态、失败保留草稿、成功自动定位项目。键盘 Tab 顺序清楚，Esc 等同取消，关闭回到触发按钮；小屏面板不截断操作区。统一中英文词条。
