# 切片搜索误填邮箱：Bug 记录与实施交接

日期：2026-09-22  
页面：`https://histopilot.com/app`  
状态：已定位过滤原因，最终修改待实施；未部署。

## 可直接用于 Note 的记录

管理员反馈「未归类切片」显示 4 张，但展开后列表为空，看起来像切片没有加载或权限异常。后续完整截图显示：侧栏顶部的切片搜索框里出现了登录邮箱。页面按这个邮箱过滤文件名，所有切片被隐藏，但数量仍显示过滤前的 4，也没有「无匹配结果」提示。搜索框只有 placeholder，填入邮箱后用途不明显，用户将它误认为账号信息。

已确认的直接原因是搜索框中的邮箱触发了列表过滤。截图中的填充背景和邮箱内容提示可能是浏览器或密码管理器自动填充；具体填充来源尚未确认。原输入框已经有 `autocomplete="off"`，因此不能只重复添加该属性就宣称解决问题。此次没有证据表明切片丢失或管理员权限故障。线上脚本及样式与排查时本地版本一致，浏览器测试中 4 张未归类切片初始加载正常。

产品决定：保留搜索能力，默认收起；用户点击「搜索切片」后才创建输入框，关闭时清空过滤并移除输入框。配合自动填充防护、明确的搜索用途和无匹配提示，避免再次出现「有数量、无列表、无解释」的状态。

## 证据与边界

- 最初截图：项目为空，未归类计数为 4，展开区域没有切片行。
- 后续截图：顶部搜索输入框中有邮箱，未归类区域展开后仍为空；控制台截图没有页面报错。
- 初始诊断语句粘贴后出现的 `Unexpected token '.'` 是诊断执行失败，不能当作业务页面报错或据此推断浏览器版本。
- Chromium fixture 重现：管理员、无项目、4 张未归类切片时初始均可显示；输入不匹配的邮箱可使列表变空。
- 另一个已复现缺陷：`applySlideFilter` 使用 `data-name || row.textContent`，由于文件名存在，实际不匹配显示的别名。保留搜索时一起修正。
- 尚未进行真实密码管理器自动填充测试，也未收到用户清空输入框后的结果；不要把自动填充来源写成已确定事实。
- Note 和测试只使用虚构邮箱，例如 `owner@example.test`，不复制用户真实邮箱。

## 最终修改方案

### 1. 搜索框按需创建

- 修改 `templates/_app_shell.html` 的正式工作台分支：默认只渲染「搜索切片」按钮和空容器，不渲染搜索 input。仅 `hidden` 或 CSS 隐藏不足以满足此方案。
- 点击按钮后，在 `static/app.js` 中创建 `type="search"` 输入框并聚焦；设置明确的可访问名称、placeholder 和用途标签，不能仅靠 placeholder 表明用途。
- 按钮维护 `aria-expanded`、`aria-controls`；提供带名称和 tooltip 的关闭按钮。
- 关闭搜索时清空查询、恢复全部可见切片、移除 input、更新展开状态，并将焦点返回搜索按钮。
- Escape 在搜索框中关闭搜索，并阻止同一个事件继续关闭手机侧栏。普通打开侧栏或点击「选择切片」不应自动创建输入框。
- 侧栏收起/展开时，如保留正在使用的搜索条件，应保持搜索区域展开、条件可见；不能留下用户看不到的过滤条件。
- Demo 分支的搜索属于 `static/demo.js`，本次不扩展修改到 Demo、百度导入搜索等其他入口。

### 2. 自动填充防护

- 创建输入框时设置 `autocomplete="off"`、非账号含义的字段名称，如 `slide-filter`，以及合适的密码管理器忽略属性；这些只作为辅助措施。
- 在读取搜索值及处理 input/change 时，检测浏览器原生 autofill 状态。选择器能力检测需兼容不支持的浏览器，不能让检测异常中断列表加载。
- 对明确标记为自动填充的值清空并恢复列表。不要按「包含 @」或「看起来像邮箱」一概拒绝：用户可能主动搜索合法文件名或别名。
- 不使用持续清空输入框的定时器，避免破坏中文输入法、粘贴和用户正常输入。
- 不宣称能够禁止所有扩展注入。主要保障是首次加载没有搜索输入框，以及出现过滤时用途、条件、结果与退出方式都清楚可见。

### 3. 搜索行为与反馈

- 修正 `applySlideFilter`：同时匹配完整文件名与别名，保留大小写不敏感的行为。
- 搜索命中项目名称时，项目中的切片应可见，与现有函数注释承诺一致；只命中切片时展示并展开所属项目。
- 无匹配时展示「没有匹配的切片」，不要显示空白列表，也不要误写成没有上传切片。
- 未归类计数在过滤时显示匹配数/总数，例如 `0/4`，清空后恢复 `4`。
- 列表重新加载时应用当前有效查询；没有搜索输入框时默认显示全部，不能从已移除的 DOM 引用读取旧查询。
- 新文案补齐 `static/i18n.js` 中英双语；样式沿用现有按钮和侧栏样式。
- 检查 `els.slideSearch` 的所有引用、`reloadProjectsAndUnfiled`、侧栏 `focusSearch` 回调和空态「选择切片」入口。动态创建/移除后需正确更新引用，避免遗留已脱离 DOM 的 input。
- 若最终发布修改过的静态资源，按仓库惯例更新 `templates/index.html` 对应资源版本参数；发布行为单独执行，不把本交接文档当作已发布记录。

## 测试与验收

使用虚构管理员身份、空项目列表和 4 张未归类切片。测试真实生产模板、脚本和 CSS，可复用 `tests/e2e/toolbar-account-upgrade.spec.ts` 的 fixture。

1. 初始加载和打开侧栏：搜索 input 在 DOM 中不存在；计数为 4，4 行都可见。点击「选择切片」同样不创建搜索 input。
2. 点击搜索按钮：只创建一个输入框，焦点正确；反复开关不重复绑定事件，不生成重复 id。
3. 正常查询：文件名、别名、大小写、中文输入和粘贴均可用；输入 `owner@example.test` 没有匹配时显示提示与 `0/4`，证明没有误禁正常输入。
4. 关闭搜索：4 行恢复，输入框从 DOM 移除；重新打开为空查询。Escape 行为和手机抽屉行为符合方案。
5. 自动填充：模拟原生 autofill 标记验证过滤防护；测试报告明确这是模拟。另用实际浏览器及密码管理器尝试账号自动填充，记录浏览器/扩展版本和结果，不用模拟测试代替实测结论。
6. 项目场景：项目名命中、项目内切片命中、无匹配及清空恢复均正确；无项目和无切片的真实空态不受影响。
7. 列表重载：存在查询时刷新数据仍按查询显示；关闭搜索后重载全部显示。侧栏折叠和再展开不会留下隐藏查询。
8. 视口：桌面 1440×900、用户截图的 441×975、手机 390×844。截图检查搜索控件、关闭按钮、计数和提示不遮挡；fixture 必须包含 viewport meta。确认 Console 没有新增错误。
9. 基础回归：切片点击打开、勾选、新建项目及分享入口正常；Demo 搜索维持原状。
