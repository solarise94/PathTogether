# 切片工具简化、上传进度与格式扩展实施计划

日期：2026-10-03。状态：设计待实施。对应 [review](tool-ux-and-upload-progress-review-20261003.md)。本文件不代表任何新增功能已经实现或部署。

## 1. 范围和实施顺序

| 阶段 | 交付 | 独立发布条件 |
| --- | --- | --- |
| U1 | 两个入口共用、字节级 COS 上传进度 | 传输/取消/续传合同回归及真实小文件 CORS 验证 |
| U2 | 拖放、自动识别、默认配置、折叠高级项 | 新旧任务恢复、隐私、保存与一键上传完整通过 |

| F2 | SVS/JPEG 2000 | 解码器依赖、WASM 预算及颜色验证后单独开放 |

## 2. U1：共享 COS 上传进度

### 2.1 传输适配

改动入口：`static/upload/cos-uploader.js` 的 `putPart()` 与进度聚合。仅 COS PUT 使用 XHR；控制 API 继续注入 `apiFetch`，两者认证边界保持。

1. 对每个分片建立 XHR，绑定 upload progress、错误、取消、超时和最终响应。
2. `withCredentials=false`；不添加平台 CSRF/Authorization 头，不手设 Content-Length，不输出预签名 URL。
3. 监听注册在 send 前，并测试各目标浏览器的 open/监听顺序；跨域 PUT 本来需要预检，增加监听后仍核对真实桶 CORS。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/upload)
4. 从 source.slice 取得当前分片，继续限制分片并发；不把整个 File/OPFS 输出读入 RAM。不得只为制造进度而缩小所有分片、增加请求数。
5. HTTP 非 2xx 才返回失败；upload.load / loadend 不作为成功凭据。响应 ETag 读取遵循现有语义，服务端核对仍是权威。
6. 接入现有 AbortController；取消会 abort 全部活动 XHR、停止计时/签名/轮询，注销监听。刷新/重试仍用同一 ingestion 与已确认分片。
7. 保留现有重试次数、续签、首次记录写入屏障、跨标签锁、账号归属和取消后禁止记录复活。
8. XHR network error 映射到现有 `network` 错误合同；不能依赖只有 fetch 才会产生的 TypeError。已有单片重试、续签和失败 UI 的分类一起核对。

### 2.2 字节算法与事件合同

```text
confirmedBytes = 冻结计划中已确认的唯一分片长度之和
activeBytes = 当前各分片最新有效尝试的 loaded 之和（每片夹到实际长度）
loadedBytes = min(totalBytes, confirmedBytes + activeBytes)
frac = loadedBytes / totalBytes
```

- `totalBytes` 必须与 source.size 和计划长度之和一致；输入异常时拒绝，不制造百分比。
- 片号只记一次；重试分配新的 attempt ID。旧尝试的迟到回调无效；失败尝试的 loaded 不计入下一次尝试。
- PUT 成功后，同一更新移除 activeBytes、加入 confirmedBytes，不能双计数。恢复记录只持久化已确认分片，不把 upload progress 写成持久完成。
- 重试可能使暂态百分比回退，明确提示“正在重试”；不使用历史最大值冒充已确认传输。刷新先以已确认数据恢复进度。
- 未收到可用长度事件时展示活动状态；按分片响应更新已确认字节作为后备。短文件不能只依赖分片完成事件作为验收。
- 请求 body 发送到 100% 后，若 HTTP 响应未确认，显示“数据已发送，等待确认”。不显示“完成”。

兼容原事件的扩展建议：

```js
{ type: 'progress', phase: 'uploading', frac,
  loadedBytes, confirmedBytes, totalBytes, determinate: true }
```

DOM 更新最多每 100–250 ms；状态切换、失败、取消和最终确认立即更新。先保持现有 `frac` 消费者兼容，再统一改两处 UI。

### 2.3 两个入口的显示

- 工具：在当前选中任务的结果面板增加上传进度条、字节文本、阶段描述；其他任务的事件不能污染当前面板。切换任务后重画该任务的状态。
- 工作台：沿用已有每文件上传行，接入新字节进度；不要另造上传实现。
- 两者展示：排队 → 上传至腾讯云 → 工作台接收 → 校验/发布 → 可查看。平台下载阶段可用服务端 `downloaded_bytes / declared_size`；无量化信息的阶段用活动指示。
- 所有百分比只表示当前阶段，不合成虚假的全流程百分比；100% 上传后继续等待 viewer readiness 和目标项目关联。
- 条具备 progressbar 语义、aria-valuenow 或不定值状态。读屏状态播报节流；不要每一个网络事件都播报。

### 2.4 必要验收

1. 网络限速下，一片文件在 PUT 完成前有多次可见字节更新；禁止仅断言“产生过 progress”。
2. 大片 + 很短尾片，百分比按 bytes；多片并发不超过 100%。
3. 重试、续签、403、断网、取消及迟到成功不双计、不误完成、不复活已删除记录。
4. 刷新/同账号重登录沿用 ingestion；不同账号按现有归属流程处理。
5. COS PUT 完成、平台下载未完成时，页面仍显示接收/验证，最终成功只在 viewable 与项目关联完成之后。
6. 两入口共享事件通过；任务切换和任务行重画不串进度。
7. 使用小型合成产物做真实 COS/CORS 检查，保留方法/域名/状态和字节汇总，隐藏签名和账号；确认清理完成。大文件预算测试可沿用受控环境，真实低内存设备仍独立标记。

覆盖现有 `tests/js/cos-uploader-shared.test.ts`、`cos-upload.test.ts`、`tools-upload-feedback.test.ts` 和 C4/R1 browser suites。新增测试针对上述用户可见合同，而非逐行复写聚合函数。

## 3. U2：页面简化

### 3.1 默认界面

首屏：标题、简短本地处理说明、大拖放区与选择文件按钮。采用站点现有颜色和布局；用户截图作为结构参考，不复制无关 PDF 功能。

识别后只显示：文件名/大小、类型/模态、输出摘要、画质选择（已可用的模式）、“更多选项”和两个动作：“转换并上传到工作台”“仅转换”。完成后明确提供“保存到电脑”，不要把生成 OPFS 文件说成已经保存。

高级设置：

- 内存档位默认沿用 `defaultProfileId()`；未知设备用保守档位，较快档位仍需主动选择。自动值不表示测得真实可用内存。
- 明场默认 bf-ome；“兼容 OpenSlide 工具”选择 bf-classic。面向用户按目标软件表达，仍保留真实格式和扩展名。
- 像素严格无损规则放高级项，文字说明可能拒绝转换，不能和“高质量”合并。
- 荧光默认 fl-ome；识别后才显示可选通道信息上传，不显示不适用的经典明场格式。
- 文件技术摘要、空间细项及任务日志折叠。空间不足/不确定确认不能折叠隐藏。

### 3.2 交互和任务兼容

1. file input 和 drop 都进入同一 `prepareSource` 流程；阻止默认导航。键盘、触屏选择文件依旧可用。
2. U2 第一版只接受一个切片文件；多文件拖入提示当前限制，不静默丢弃。MRXS 未实现时提示需要完整包且当前未支持。
3. 扩展名用于提示，有限 header/结构检查用于识别。已知不支持文件在完整复制前拒绝；目前 KFB/KFBF 检查原样保留。
4. 首次选择可以按现有逻辑做本地准备；大空间确认后才复制。准备与转换显示不同阶段，支持取消准备。
5. 识别文件后自动推荐，不替用户立即上传。只有上传按钮的明确动作或既有工作台上传意图授权网络操作。
6. 准备状态可改输出 profile，并保存任务；开始后锁定所有影响输出的设置。重开任务以已保存记录为准，不能被隐藏默认选项覆盖。
7. 老任务没有 outputProfile 时保持 classic；新默认不修改旧任务。未来 quality/adapter 字段缺失时映射原有保留编码语义。
8. 工作台传文件/项目给弹窗仍支持，来源校验、目标项目、重试关联和重复点击幂等原样保留。
9. 上传限额继续取登录 endpoint 的十进制 bytes，不写死 10 GiB；当前生产上限 9,500,000,000 B。超限产物只关闭上传，仍可保存。
10. 本地转换页未授权上传时无 `/api/` 请求；不增加遥测上传文件名/哈希。转换加载后离线可用能力保持。

### 3.3 U2 验收

拖放/键盘入口、伪装后缀、未支持文件、取消、空间确认、KFBF 可选 channel.json、刷新保存配置、prepared 修改、运行后锁定、旧 classic 恢复、离线、取消上传保留产物、项目关联失败重试、换账号和清理均覆盖。中英文、窄屏和折叠项检查一次；优先复用已有 C3/C4/R1 真应用场景。

纯 UI 简化后，现有模式产物应与改版前字节一致。U2 不自动带入 U3 的编码变化。

## 4. U3：简单质量选项的真实含义

| 用户名称 | 内部策略 | 限制 |
| --- | --- | --- |
| 保留画质（推荐） | `preserve-source-v1`：兼容 tile 直接搬运，必要边缘处理 | 当前能力；不叫严格无损 |
| 更小文件（有损） | `compact-jpeg-v1`：逐 tile 解码并以固定参数重编码 | 新增能力；仅明场，体积变小不保证所有输入成立 |

U2 发布时若 U3 尚未完成，只展示推荐模式，不提供可点击的占位功能。质量独立于 bf-ome / bf-classic：四种组合各有明确输出合同，不能把 OME 当作高质量、classic 当作压缩。

U3 实施要求：

- 先评估当前 JPEG 核心是否具备通用编码所需能力，再确定 WASM 实现和速度预算；不能假设边缘处理器等于通用压缩器。
- 固定 quality、采样、色彩解释、编码器版本及金字塔处理策略。首轮可比较 Q80/Q85/Q90 候选，测完再锁参数；不要提前承诺某压缩率。
- 默认保留全部源分辨率与坐标，不裁剪、不缩小；不以降分辨率实现“压缩”而不告知。
- 每次只保留有界 tile/codec scratch；受内存档位约束；检查输出超过预估空间、取消与断点恢复。
- 任务、journal 和 checkpoint 同时固定 `encodingProfile`、参数指纹、writer/adapter 版本。续跑参数不同则拒绝，绝不混合两种质量的半成品。
- 计数复制/重编码/填充 tile，输出报告记录新增有损处理；源已压缩的事实保留。颜色、MPP、objective、层级与元数据规则不变。
- 内置验证针对 compact 结果本身；不能继续要求 browser/native compact 与 preserve 字节相同。相同 compact profile 的 browser/native 字节一致性需单独验收。

验收先用边缘、奇数尺寸、各种 JPEG 采样和纹理/低对比/高饱和样本，记录大小、时间、峰值内存、解码色差及人工盲评；未经阈值评审不默认推荐给定量用途。荧光不提供此有损模式。

## 5. 格式扩展架构

### 5.1 分离输入适配、像素处理和输出

```text
单文件/完整包
  → 有限读取识别 + 能力报告
  → OPFS 源副本 + 来源清单
  → SourceAdapter（元数据、层级、region/tile）
  → 编码策略（保留 / 重编码 / 必要的区域组装）
  → writer（明场 OME / classic，荧光 OME）
  → 结构与像素验证 → 本地保存 / 现有 COS uploader
```

当前浏览器输入能力与平台原生 reader 能力分开登记，共享格式 ID/描述映射但不共用“能打开”的布尔值。报告应区分可识别、可转换的变体、需要 companion、模态/通道可信度、编码器要求和具体拒绝理由。

适配器返回实际层级尺寸/downsample、tile shape、codec、photometric/sampling、通道/轴、标尺来源与颜色配置。不能把源 tile 默认成当前 KFB 的尺寸；writer 必须显式处理不同 tile 布局。

保留模式仅在源 codec 与目标 TIFF 标签、JPEG tables、采样、边缘几何完全兼容时直搬，否则拒绝或明确选择已实现的重编码路径。禁止复制错误标签，或把 JPEG 2000 bytes 放进 JPEG 压缩的 TIFF。

### 5.2 F1：SVS/JPEG 首批合同

- bounded TIFF/BigTIFF 解析：字节序、64 位偏移、IFD/SubIFD 链、指针循环、维度溢出和文件边界；不能只 sniff `II`/`MM` 后便复制整个未知文件。
- 识别 Aperio 描述、主图和真正降采样层；缩略图、label、macro 不当成金字塔。未知多 series/荧光页包先拒绝。
- JPEG tile 能否搬运按 codec/标签验证，支持共享 JPEGTables 的源需要正确合并/表达；非当前 tile 尺寸不能写假 tile 标签。
- 保存可信 MPP/objective、ICC 或有明确来源的色彩处理；缺值保持未知。label 默认不导出，避免携带标签信息；说明这是主图转换，不是源文件归档。
- 支持矩阵按实际样本变体开放，JPEG 2000、非支持 planar 配置等明确拒绝。
- 原始 SVS 若只为平台查看，保持工作台已有原生上传路径；转换是用户选择的兼容输出，不强制所有 SVS 重新压缩。

SVS 结构及 codec 来源：[OpenSlide Aperio](https://openslide.org/formats/aperio/)。只引用格式结构；原生库支持不作为浏览器实现证明。

F1 验收：合法/恶意小 fixture、经典 TIFF/BigTIFF、不同 tile 形状、尾边缘、label 排除、ICC、缺 MPP、JPEG2000 拒绝、browser/native 同 profile 一致、层层 ROI/完整性、QuPath/OpenSlide 各自兼容、平台实际 reader 和 viewer。用户文件保持私有，不提交客户标签或扫描器标识。

### 5.3 F2：JPEG 2000

先做独立可行性验证：解码器许可证与打包、WASM 构建、YCbCr/MCT、实际采样、tile 解码内存及速度。目标继续 JPEG 时会发生新有损编码；不能宣传无损搬运。若要无损目标 codec，另增加 writer/reader profile 合同并测产物体积。不把 F2 放进 F1 的通过清单。

### 5.4 F3：MRXS 完整包

输入 UI 至少提供完整父目录选择；拖文件夹按浏览器能力启用，并提供可靠的目录选择后备。典型包包括 `.mrxs` 主入口、同名目录与 INI/Index/DAT。只拖 `.mrxs` 或单个 `.dat` 时显示缺失成员，不启动大规模复制。

- 单个逻辑切片的 source manifest：规范相对路径、成员大小/哈希、总量、根摘要、入口、adapter 版本；拒绝越界路径、重复冲突及结构不完整。
- 按成员逐个、单缓冲复制到 OPFS；manifest 与复制进度落盘。源未复制完整的记录不得当成可直接恢复的准备完成任务。
- 完整包复制后，刷新/恢复使用 OPFS 成员，验证清单/大小/摘要；不靠浏览器继续持有原目录授权。
- 文件数、目录项与索引本身也计入内存预算；大索引分页/溢写，不把整个目录/索引都无限留在 JS heap。
- 解析真实位置、重叠、稀疏区、层级与拼接信息，按有界输出区域合成；坏索引、缺图、解码失败不能当白背景吞掉。
- 不默认裁剪；如日后增加裁剪，记录 source/output 坐标变换并传播到标注与分析。
- 原生 OpenSlide 可作独立 ROI 对照；移植完整 OpenSlide/WASM 与实现受限 MRXS adapter 分别评估，不能宣称已有 C 库可直接在网页运行。

结构来源：[OpenSlide MIRAX](https://openslide.org/formats/mirax/)。MRXS 的复杂拼接可能必须重编码；保留画质模式的实际处理说明按该 adapter 展示，不能承诺任意 bundle tile 都能直搬。

F3 验收：缺主入口/目录/成员、源更改、异常路径、循环索引、不同位置表版本、稀疏空区、重叠/非整数偏移、跨 tile/跨层参考 ROI、奇数边缘、复制中断、恢复哈希、删除目录清理及真实内存测试。先支持明场；多通道荧光须有独立通道合同。

## 6. 交付、上线与回退

每阶段独立提交并附支持矩阵、准确命令/版本/输入摘要/退出码，缺样本的场景明确未运行。不能先写“通过”再补测。U1/U2 不要求重跑所有格式外部检查，但必须跑共享上传器与受影响恢复链路；新增 codec/adapter 后才扩大相应测试。

上线先候选环境，用小型合成数据完成真实 COS 和平台接收检查，再按授权发布；真实系统保存对话框、Windows 和真实 4/8 GB 设备独立记录。Mac 的本轮用户确认记为已能打开，不扩大其证明范围。

JS/WASM/manifest 版本一致发布。旧任务缺字段继续映射旧语义；新编码/adapter 引入 journal schema 时明确兼容范围。回退不得让旧运行器接着写新 profile 的半成品；保存本地任务，恢复兼容版本后再继续。UI 回退与核心回退分开评估，不删除 OPFS 来规避恢复问题。

COS 暂存池保持现有容量、清理及释放合同：删除当前版本、旧版本、delete markers 和 multipart 确认后释放预约；清理失败继续占用，不以页面显示成功代替桶清理成功。新 UI 不修改生产额度或桶策略。
