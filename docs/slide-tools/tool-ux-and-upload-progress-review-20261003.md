# 切片工具体验、COS 进度与输入格式 review

日期：2026-10-03。范围：源码 review、线上只读核对和实现建议；本轮没有修改应用、上传新文件或部署。

源码基线：`release/r1` 的 `7aa4d88`；生产应用来自 `r1-rc6` / `8127ecb`。用户明确反馈缺进度条的入口为**转换并上传**。用户已再次确认 Mac 可以读取转换产物；本轮不把 Windows、真实系统保存对话框或真实低内存设备记为通过。

## 1. 结论

1. **COS 上传进度条可以做。** 当前工具页没有上传条；共享上传器只在整片 PUT 成功后报告分片数量进度。因此单分片文件往往只显示 0% → 100%，大分片也会长时间没有变化。
2. **转换并上传确实使用腾讯云 COS。** 浏览器本地转换 → 预签名 COS 分片 PUT → 平台从 COS 下载、验证、发布 → 清理远端暂存对象。页面上的“直传”指浏览器直传 COS。
3. **页面可先简化，保持当前转换语义。** 默认 OME-TIFF、自动内存档位、保留已有编码；拖放/选文件为主入口，技术选项折叠。
4. **画质与输出格式是两件事。** OME-TIFF / 经典 TIFF 是布局与软件兼容性；是否重新压缩才影响额外损失、大小和速度。当前没有全片可调 JPEG 质量模式。
5. **格式扩展分阶段。** 先覆盖明确的单文件明场 SVS/JPEG 变体，再评估 JPEG 2000，MRXS 需要完整多文件包及几何处理。赛维尔按用户最新决定暂缓，等待实际文件；不列入本次实现范围。

实施任务和验收标准见 [实现文档](tool-ux-and-format-expansion-implementation-plan-20261003.md)。

## 2. Review findings

### F1 · P2：转换工具缺少上传进度条（确认）

- `templates/tools_slides.html` 的 `#upload-block` 只有上传/取消按钮和 `#upload-status`；复制和转换各有进度条，上传没有。
- `static/tools/tools-slides-upload.js:628` 接到 progress 后仅调用 `setStageTxt()`，拼接百分比文字。
- 同文件 `paint()` 只重画状态文本；任务行的“查看上传进度”按钮实际切换到这个结果面板。

影响：用户无法直观看到转换后的网络传输，容易以为停止工作或走错链路。增加纯视觉条只能改善外观，不能消除 F2 的停顿。

### F2 · P2：上传进度只有分片完成事件，且按片数计算（确认）

- `static/upload/cos-uploader.js:98` 的 `putPart()` 使用 `fetch`，没有上传字节回调。
- `confirmPart()` 在 PUT 返回成功后用 `totalConfirmed / plan.length` 发事件。
- 分片长度在冻结计划中已存在，最后一片可能比其他片短；按片数计算不是字节百分比。
- 工作台 `static/app.js:7023` 已有上传条，但使用同一事件，所以也受粗粒度进度影响。

建议：COS 分片 PUT 改用 `XMLHttpRequest.upload` 监测传输；按实际字节加权，完成状态仍由 HTTP 响应、服务端校验和可查看状态决定。XHR 提供上传进度事件；跨域上传监听需要考虑预检。[MDN：XMLHttpRequest.upload](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/upload)

### F3 · P2：默认页面要求普通用户理解多项技术设置（确认）

当前顺序包括输入、channel.json、复制与探测、文件信息、空间预估、资源档位、像素策略、输出布局、转换、结果及任务列表。`templates/tools_slides.html:47` 起可见这些独立区块。

- channel.json 在不知道文件模态前就出现。
- 192/384/768 MiB 档位、tile 边缘重编码和 SubIFD 软件兼容性会增加理解成本。
- 没有拖放入口；主输入明确接受 KFB/KFBF。

建议：参考用户截图的中心拖放区，识别后出现单张配置摘要和动作按钮；其余进入“更多选项”和“任务记录”。保留必要的空间确认、上传授权、结果尚未保存及账号归属提示。

### F4 · 设计约束：不能把现有策略改名为两种压缩质量

`engine.js` 中资源 profile 控制内存；output profile 控制容器布局；当前 `allow-edge` / `strict-lossless` 控制是否允许边缘重编码。Rust `convert_bf.rs` 会在严格模式发现需要处理的边缘块时拒绝，并非改用一种新的无损压缩器。

因此：

- 默认可命名“保留画质（推荐）”，说明尽量保留原编码，边缘可能重编码，不承诺像素无损。
- “更小文件（有损）”需要独立编码策略、版本化参数和验收；尚未实现时不展示成可用选择。
- 原始 JPEG 本身可能有损；后续无损存储不能恢复此前损失。
- 荧光定量数据默认不增加有损压缩，不把显示窗口或伪彩写入分析像素。

### F5 · 能力边界：平台能查看 SVS/MRXS，不等于浏览器能转换

- `slide_format_registry.py` 登记 SVS 为原生单文件，MRXS 为 native-bundle。这是平台 reader/上传能力。
- 浏览器 `static/tools/slide-transform/engine.js:370` 的快速签名筛选仅覆盖 KFB/KFBF；Rust 核心当前输入适配也是这两类。
- 只改 `accept`、扩展名白名单或引入原生 OpenSlide 名称不能完成 WASM 转换支持。

## 3. COS 链路与用量核对

### 本轮核对的证据

- 当前 `pathtogether-demo` 使用 `suite-20261003`。
- 公网、生产容器、review 工作树的 `static/upload/cos-uploader.js` SHA-256 一致：`e0bf4181b041426adcc16c08e84dfb3f7fd2117c299b6a87dea2f34193a6c116`。
- 工具控制器调用 `HP_COS_UPLOAD.createUpload()`；申请 `/api/ingestions/<id>/parts/sign` 后，字节经独立 COS PUT 发送。控制 API 不携带整个转换文件。
- 生产数据库在显式只读事务中的近 24 小时汇总：15 个任务，桶 `histopilot-1255456712`，transport `presign_parts`，合计 381,108,584 bytes。15 个任务均 completed、记录 COS version、下载字节等于申报字节、远端清理 cleaned。该汇总包含验收任务，不能定位用户某一次上传，也不替代腾讯云账单。
- 既有 [rc6 生产验收](../review-evidence/slide-tools/R1/rc6-production-20261003.md) 有真实 COS PUT 和清理证据。本轮没有再次发起付费流量测试。

### 为什么后台可能看不见

COS 是临时中转；平台取回并完成清理后，当前存储占用可以回到零。版本和未完成分片的清理也必须完成，容量预约才可释放。

普通外网上行流量免费；COS 向 homePC 这样的本地服务器下载产生外网下行流量。资源包抵扣量与上传字节不是同一指标，存储容量包按当天平均存储量抵扣。因此“桶当前为空”或“资源包用量很少”不足以证明绕过 COS。[腾讯云：流量费用](https://cloud.tencent.com/document/product/436/53863)、[资源包介绍](https://cloud.tencent.com/document/product/436/36523)

用户随后确认所查看的控制台数据有一天延迟，撤回对上传链路的疑问。本轮没有独立取得腾讯云监控/账单数据；一天延迟记为用户确认的页面行为，不泛化到所有监控指标。上传链路不因这个显示延迟做功能改动。

[转换并上传到工作台]  [仅转换]

简化不意味着省略异常处理：大文件空间不确定确认、登录失效、不同账号续传、超过上传上限时保留本地保存，都继续显示。荧光识别后才显示“通道信息（可选）”，缺失元数据时不猜 marker。

## 5. 扩展格式建议

| 输入 | 当前浏览器转换 | 拟议处理 | 边界 |
| --- | --- | --- | --- |
| 已验证 KFB/KFBF | 支持 | 保持现有转换及恢复合同 | 新变体不自动放行 |
| 常规明场 SVS，JPEG | 不支持 | 第一批新增适配；兼容时复用 tile 编码 | 排除 thumbnail/label/macro，识别真正分辨率层 |
| SVS，JPEG 2000 | 不支持 | 后续独立解码器与预算验证 | 不能套用 JPEG 直搬路径 |
| 标准 MRXS | 不支持 | 完整包选择、索引与扫描位置处理后转换 | 不接受只有 .mrxs 主文件 |
| 赛维尔 SVS / DAT 交付 | 暂缓 | 用户提供实际样本后另评估 | 品牌不是统一格式，不承诺通道可恢复 |
| 其他 TIFF/厂家格式 | 未统一支持 | 逐个 layout/codec 白名单 | TIFF 签名不是通用转换通过条件 |

SVS 的 TIFF 结构含关联图；某些 Aperio 压缩使用 JPEG 2000。MRXS 是多文件格式，索引和扫描位置包含重叠信息，不能仅按网格拼接。[OpenSlide：Aperio](https://openslide.org/formats/aperio/)、[MIRAX](https://openslide.org/formats/mirax/)

仓库已有 [赛维尔历史方案](../servicebio-download-conversion-plan-20260919.md)，记录了 SVS 多页通道与 INI/Index/DAT 包的样本差异；它是历史参考，含旧后台转换架构，不能直接套用或视作通用支持的验收记录。本次不启动其下载、通道提取或服务器转换工作。

## 6. 已知问题的状态与后续

- **新 ID 切片的 AI 会话列表 403：仍未修复，P1 独立跟进。** 生产验收中，切片 owner 可读 info/tiles，但 `/api/ai/sessions?slide=<slide_id>` 被旧权限入口拒绝；见 rc6 生产报告。此次 UI/进度计划不会自动解决它，修复需保持跨用户隔离。
- **`[object Object]` 上传错误文案：当前源码已有修复。** `describeUploadError()` 和 `tests/js/tools-upload-feedback.test.ts` 已覆盖等待任务上限等结构化错误。本轮不重复列为未修复 bug，也没有重新触发线上错误。
- **Mac ARM 打开转换文件：用户确认通过。** 不把单次打开扩大为所有样本、项目重开、Windows或内存设备通过。

优先次序：共享上传进度修复 → 页面简化 → 小文件模式编码 → SVS/JPEG → MRXS。赛维尔等待样本后再排期。AI 会话权限问题作为独立任务并行排队，不混进格式功能提交。
