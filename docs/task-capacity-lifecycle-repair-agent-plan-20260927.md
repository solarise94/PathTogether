# 上传容量生命周期修复执行方案

日期：2026-09-27。代码核对基线：PathTogether `c1d2b6d`。

本文是待实施方案，不是修复完成报告。只涉及上传容量责任、租约、清理和对应测试；不授权生产迁移、部署或打开 COS capability。沿用 [slide ID 重构方案](slide-id-storage-refactor-agent-plan-20260925.md) 与 [迁移审计 runbook](slide-storage-migration-audit-runbook-20260925.md)，本文替代其与下述容量生命周期相冲突的约定。

## 1. 结论与范围

采用“任务持有容量，租约控制执行”的模型，继续使用 `upload_reservations` 和 `upload_user_quotas`，不新增第二套容量账本，不重写上传协议、资产 ID 或 COS 远端池。

**任务停止心跳不代表字节消失。** 已交给任务的预约不能被其他上传按 TTL 回收。任务成功发布时转实占；任务放弃时，在停止写入且清理确认后释放。租约到期只触发恢复或清理编排。

本次需要同时修正 R11 的恢复语义与验收测试。仅给 `released` 分支补一次重新准入，可以修复眼前反例，却保留了“先漏账，再补账”的设计，不作为最终实现。

覆盖所有使用本地预约的 writer：V1/V2、COS、百度导入、ZIP、转换及维护路径。允许分提交落地；所有调用方切换和旧分支拆除完成后，才宣布本方案完成。配额豁免身份保持现有产品规则，但必须显式识别，不能用“预约缺失”推断豁免。

## 3. 必须成立的不变量

1. 每个需要本地容量的未结算任务，都有归属、用途、字节数明确的容量责任；等待准入、尚无写入的任务可以没有预约。清理中的残留同样必须有责任。
2. `quota.reserved_bytes = SUM(reserved_bytes WHERE state='reserved')`，与租约是否过期无关。仅该等式不足以验收，还须检查任务到预约的完整绑定。
3. 每份责任只计一次。发布结算和清理释放互斥、幂等；状态只能 `reserved → consumed` 或 `reserved → released`。正常运行不允许 released → reserved。
4. 预约归属和任务归属必须一致；任务不能借用另一任务的预约。显式共享批次预算按批次记一次，不能复制到每个子任务重复收费。
5. 续租不创建预约，不计为新上传，不消耗新的每小时请求名额，也不执行准入回收。业务绝对截止时间不能被心跳无限延长。
6. 任务的终态与清理终态分开：FAILED/CANCELLED 可以仍有待清理责任；清理失败、重试耗尽、进程崩溃均不能自动释放。
7. 清理成功必须意味着旧 writer 不能再写入同一待清理区域。只检查一次目录不存在不足以证明这一点。
8. 本地容量和 COS 池是不同资源；各自根据实际结算或清理证据释放，不能互相代替。

## 4. 数据与接口设计

### 4.1 在现有预约表表达持有者

扩展 `upload_reservations`，迁移编号选择实施时下一个空闲号：

- `holder_kind`、`holder_id`、`purpose`：持有任务/批次及用途。种类为有限枚举，不允许任意字符串形成新的通用工作流框架。
- 未绑定字段全空；绑定字段必须完整。绑定后不能用普通 renew/release 修改归属。按持有者和用途建立“未结算责任唯一”的约束；需要多份预算的通道必须显式区分用途。
- 保留现有 state、字节、时间字段。`expires_at` 对未绑定预约仍是可回收截止时间；对已绑定预约仅表示执行租约时效，不控制是否计入容量。
- 如果迁移需新建补账预约，记录明确的来源（正常准入/迁移核账），每小时准入计数只统计正常准入。不要靠伪造 `reserved_at` 隐藏修复记录。

采用任务类型加 ID 的绑定无法直接用一个普通外键约束多个任务表，因此创建/绑定必须同事务校验，审计必须双向检查悬挂、重复、跨 owner 绑定。不要声称唯一索引能证明任务存在。具体枚举和批次用途由第 A 阶段清单确定并固定在迁移与代码中。

未绑定预约只能存在于“尚未开始产生字节”的准备阶段。任何 writer 启动前都必须完成绑定。能直接同事务创建任务与预约的入口应直接绑定，不制造中间状态。

### 4.2 分开三个操作

对外接口名称可贴合现有命名，职责必须分开：

- **准入并绑定**：校验用户限额、速率、并发数，建立任务和责任，原子提交。补占仍在同一责任上增加字节，同事务更新配额。
- **核验并续执行租约**：在任务锁下核验可恢复状态、owner、绑定、generation、绝对截止时间。已过期但容量仍持有且任务允许恢复时，可发新执行租约；released/consumed/missing 不能经此路径恢复。
- **结算或确认清理后释放**：发布成功在发布事务内转实占；放弃任务只能经清理收口释放。不能保留一个无任务语境、可任意释放绑定预约的公开入口。

原 `reservation_is_active` 的调用逐一拆成“仍持有容量”和“当前允许执行”，不要简单全局改成只看 reserved，否则过期 worker 会被错误放行。底层财务操作使用 CAS/RETURNING；公共 wrapper 仅开事务并委托，继续保持唯一实现。

并发上传限额按业务中可执行的任务计算，清理中的任务可以不占执行槽，但仍占容量。准备阶段的未绑定有效预约也须防止绕过并发上限。计数及新准入在同用户 quota 锁内串行化；列明每种通道的计数主体，批次不能忽然改为按子文件计数。重复续租和清理重试不增加每小时上传次数。

### 4.3 不变量异常的处置

普通用户活跃任务遇到 missing/released/consumed、owner 不符或绑定不符时，拒绝新签名、下载和发布，持久化异常并进入受控恢复/清理流程；不能仅打印 conflict 后保持 uploading，也不能擅自消费他人的预约。

正常运行不自动复活 released 记录。历史坏数据由第 E 阶段一次性核账修复；若运行时再次出现，视为不变量破坏并阻断相关任务。尚存字节但责任缺失时，对受影响用户暂停新准入直至核账，避免故障期间继续透支。不要因为检测到异常就删除已发布文件。

## 5. 清理和事务边界

取消、失败、超期采用统一顺序：

1. 短事务锁任务，确认未跨不可取消的 commit-intent 边界，撤销后续执行资格并持久化清理意图；保留预约。提交成功之后才执行文件 I/O。
2. 停止或隔离旧 writer 后清理任务暂存。使用现有 generation/lease 机制，核实它是否真的防止文件写入，而不只阻止最后一次 DB UPDATE。无法中止的操作须等待结束或隔离到旧 generation 的目录，再确认删除；不能用固定 sleep 作为证明。
3. 清理成功后，短事务重验清理 token/generation 和绑定，CAS 释放预约、更新配额并标记该资源清理完成。崩溃发生在物理删除后、DB 收口前时，重复删除和收口均幂等。
4. 清理失败保留重试工作和容量，记录有界错误信息及告警。重试耗尽转人工处理，不用 TTL 自动抹掉责任。

复用已有 `upload_cleanup_pending` 和 COS 清理编排，不再添加第三个重叠队列。V1/V2 的 pending 只管理重试，不再补账；COS 在现有任务记录中分别持久化本地与远端清理进度，具体必要字段随迁移增加。远端 URL 仍可能有效、已有上传仍可能完成时，不能因本地取消就声称远端已经静止；保留原有远端清理证明与池责任。

成功发布后，资产实占与仍存在的额外源文件/转换中间件责任也要分别核对。若只有一次账本转换却暂时有两份独立物理副本，清单必须说明其配额口径和物理水位保护；不能把额外副本作为无责任残留。硬链接不得误当两份独立数据重复计算。

### 锁协议

保留 R10 已统一的 quota → reservation 顺序；任务编排先取对应 task/job 锁，再进入该财务锁序。同一事务涉及多个同类对象时按固定 ID 顺序加锁。

必须画出实际事务的完整锁依赖图，包含发布 advisory lock、slides、COS pool、批次、子任务，而非只审 helper。`slide_publish.py` 现有注释还有 reservation → quota 旧描述，应同步纠正。禁止在持有 quota 后回头等待 task/job；清理事务也不能例外。禁止持数据库锁等待网络和文件树删除。

### A. 固化反例与全调用点清单

- 保存 R11 两个场景，补 COS 本地删除失败反例。修正测试采样方法前保留原失败证据。
- `rg` 检索全部 reserve/renew/topup/consume/release、直接修改 quota/reservation 的 SQL，以及全部启动写入的位置。
- 清单逐入口记录：任务表/ID、owner、预约用途、创建与绑定事务、续租、发布、取消、超期、清理、批次分配与转交。不能只查四个 store 文件；包含 `app.py`、脚本和 worker。
- 明确百度批次及 ZIP/转换 source/output 的现有结算口径。所有权转交只能在交出方停止使用后，以同事务 CAS 完成；无转交需要就不新增转交 API。

产物：入仓反例、调用点表、实际锁图。此阶段不改变生产数据。

### B. 加模型与统一原语

添加绑定约束和兼容读取；实现职责分离。已有正常绑定责任不参与过期回收；未绑定且未开始 I/O 的短预约保留回收能力。所有记账保留事务、行锁、CAS/RETURNING 和幂等语义。

新增针对模型约束和状态转换的实库测试；过渡代码明确标记删除阶段。不要长期支持两种相互竞争的财务实现。

### C. 切换全部 writer 和清理路径

优先 COS 完整链路，再切 V1/V2、批次导入和转换。统一发布、parts/sign、续租、topup、cancel、sweep、管理员重试都使用新合同。对外错误码和任务文案反映暂停/清理状态，不把不可执行任务继续展示为正常上传。

COS 的恢复扫描不得用 `local_reservation_id IS NOT NULL` 隐藏不变量异常；quota 豁免身份单独过滤。取消/失败不再先释放后清理。检查重启、重复 DELETE、管理员 staging-residue 收口均走同一实现。

### D. 删除补丁与错误验收

全部 writer 已绑定、存量已校验后，删除：

- 任务持有预约的 TTL 自动回收，以及依赖 cleanup_pending 反连接的特殊豁免。
- `record_cleanup_pending` 中 released → reserved 和“延期 30 天”补账逻辑。
- COS 心跳通过 `reserve_upload_locked` 重新准入、替换 rid 的正常分支。
- 将活跃任务 + released/missing 当作正常 skipped 的分支。
- COS 释放后的 best-effort 清理，以及吞异常后无持久重试责任的路径。
- 重复财务 SQL、旧锁序注释、以“预约合计相等”替代任务完整性验收的断言。

原 R8/R9 复现不可直接丢掉：保留并发残留不漏账、不重复计账的场景，新断言以“责任从未释放”为目标。变更断言须注明被替代的状态机合同，不再声称这些旧实现级断言原样保留。

### E. 存量审计、修复与切换

先生成只读报告，再在停写维护窗口核账。旧版本会错误回收新绑定责任，不能与新版本混跑；恢复流量前必须停止旧 API/worker/定时清理器。生产执行另行批准，遵循原迁移 runbook 的备份与恢复要求。

| 存量 | 处置 |
|---|---|
| 任务与 reserved 预约归属、用途、金额一致 | 绑定，不新增收费；到期不等于已丢失容量 |
| 未绑定且确认未写入的预约 | 按原短租约规则释放或绑定；不得仅凭“找不到任务”就断言无文件 |
| 活跃任务指向 released/missing | 停止执行并审计实际字节；需要继续持有责任时新建带核账来源的预约并原子绑定，不修改历史 released 行 |
| 已有残留但当前额度不足 | 如实补记已有责任，必要时允许修复后的总占用超过配置上限并阻止新准入；输出超额清单，不伪装成新上传获准 |
| 尚未写入、又无法获取足够容量 | 明确结束任务，确认本地/远端无残留后收口；不能继续上传 |
| consumed、重复绑定、跨 owner 或金额无法解释 | 阻断该项切换并人工核对发布/结算证据，不自动扣第二次 used 或转移归属 |
| 终态任务但 pending/残留存在 | 补齐清理工作及责任，完成清理后释放；终态不是释放证据 |

核账脚本必须支持 dry-run、固定审计输入、幂等应用和逐项结果；并在冻结窗口内重验输入未漂移。补账不计为一次用户上传，不能靠调高用户额度掩盖差额。未知路径不得自动删除。

此模型切换之后，旧代码不理解绑定与释放条件。回滚优先恢复经过验证的整套备份，或使用理解新合同的兼容版本；不能只回滚应用二进制并保留新任务继续执行。

## 7. 确定性验收矩阵

使用真实 PostgreSQL、多连接和 Event/Barrier。屏障只安排合法交错，不在持有 quota 锁时等待另一个必须获取该锁的线程。设置测试超时，收集线程异常和每一轮返回值；随机重复只能作为补充。

| 场景 | 必须断言 |
|---|---|
| 100 字节旧任务到期；50 字节新准入先赢（额度及槽位充足） | 原 rid 仍 reserved，总预约 150；任务获合法新执行租约或按业务截止转清理，绝不能失去容量 |
| 同场景续租先赢 | 同一 rid、总预约 150；分别保存首轮及下一轮结果，后续心跳不增加预约/小时次数 |
| 连续三次恢复、进程重启 | 无无限 skipped、无新 rid 链、无重复收费 |
| 活跃任务 rid 缺失/released/consumed/跨 owner | 扫描能发现，签名/下载/发布拒绝，不复活或消费错误预约 |
| 取消/超期 × 新准入 × 删除失败 | 旧责任持续计入；任务不再获得新执行许可；重试清理后恰一次释放 |
| 清理删除成功后、财务收口前崩溃 | 重试收口成功，不漏账、不双减 |
| 旧 writer 晚返回、旧 generation 写入 | 已完成清理不得再出现无账残留；明确验证实际文件结果 |
| 发布 commit intent × 取消/续租/清理 | 既有不可取消边界保留，used/reserved 只结算一次 |
| topup × consume、release × 短预约回收 | 保留 R10 无死锁和整事务回滚断言 |
| 本地与 COS 远端分别失败 | 只释放已有清理证据对应的资源；另一份责任保留 |
| ZIP/百度批次/转换部分成功失败 | 源、中间件、产物各按合同核账；共享预算不重复计费，不提前释放 |
| 迁移重复运行、超额残留、未知绑定 | 幂等；差额可解释；未知项 no-go，计划和日志不泄露秘密 |

每个并发测试同时验证账本合计、任务绑定、执行资格、物理残留和清理责任，不接受只验证 SUM。先跑相关套件，再跑既有 Python/JS 门禁；不以本文件沿用的历史通过数字替代本轮实测。

## 8. 交付与完成标准
